# 从内核到 ui-kit：Chat 之后的基础能力审查

日期：2026-11-17。审查基线：`b117aeea644d2480ff62be0c4a004ac7c7ed0fbc`。
状态：**调研与审查，未实施**。本文不宣告 API 定稿，不授权绕过后续设计确认直接改代码。

本轮只增加文档、阅读源码与外部资料、运行已有测试；不修改运行时、原语、kit、Chat 或测试代码。
参照来源、版本和机制取舍见[调研记录](../research/ui-composition-frameworks.md)。
后续讨论已提升为[全局分层架构重设计](layered-architecture-redesign.md)：允许重排各层、删除和合并现有 API。
本文继续保存现状证据；第 5 节的局部修复顺序由新提案的迁移切片统筹，不作为独立补丁清单。

## 1. 结论与证据边界

Rust + Signals、作用域所有权、保留式 UI 和既有执行协议应继续保留。
Chat 已证明这套主干能够支持真实联网、流式文本、请求取消、列表、表单和弹层；
这不等于所有支撑 ui-kit 的基础契约都已完整。

自下而上的审查发现，当前最优先的问题不是缺少更多组件，而是：

1. **公开内容组合与内部子节点所有权的契约不一致。** 文本接受应用子节点，但富文本链接同步把
   整份子节点列表当作内部链接管理。这比按钮里的图标布局更底层。
2. **App 共享资源变更需要纳入同一套执行边界。** 主题、字体和文本引擎入口未显式统一检查
   执行阶段；首屏配置和运行中变更的入口也需要分清。
3. **文本展示能力必须建立在统一几何上。** 对齐和输入提示不能只在 kit 中叠一层绘制效果。
4. **事件层、字段包装和诊断分级已有相当一部分所需能力。** 应复用，不能因为 Chat 没用好就新增机制。

证据标记：

| 标记 | 含义 |
| --- | --- |
| 源码确认 | 当前实现直接体现的结构或缺口；不表示已运行新的复现程序 |
| 已有验证 | 已有测试或上一轮真实窗口记录支持，注明范围 |
| 待验证 | 静态调用链推导的风险，必须在实施前用有针对性的验证确认具体后果 |
| 建议 | 下一轮的设计方向，不是当前已存在的行为 |

## 2. 审查顺序与职责

| 层 | 应承担的职责 | 不应承担的职责 |
| --- | --- | --- |
| 执行与资源生命周期 | 调用资格、读写权限、所有者恢复、取消、资源释放 | Chat 的回答替换、排队参数、供应商策略 |
| Kernel 内容与布局 | 内容种类、子节点所有权、测量、布局、展示几何 | 为某个按钮特殊补宽度或图标偏移 |
| 文本与编辑 | 文本布局、光标、选择、组合输入、真实编辑值与提示的区分 | 保存业务表单、推测数字业务含义 |
| 语义与输入 | 名称、角色、动作、焦点、命中、输入路由 | 从任意复杂子树猜测业务标签 |
| View 原语 | 把有效组合表达出来，建立绑定、事件层与结构作用域 | 将非法内容组合延迟到绘制阶段才暴露 |
| ui-kit | 按钮内容、字段、数字编辑、对话框等可复用交互模式 | 第二套事件分发、编辑器、生命周期或权限系统 |
| Chat | 请求快照、验证规则、持久化、产品布局与业务流程 | 自建诊断严重性标准、替代基础文本布局 |

顺序是依赖关系，不意味着需要依次重写这些层。已满足契约的层直接保留。

## 3. 审查发现

### F1：文本的应用子节点与内部链接子节点存在所有权冲突

优先级：高。归属：Kernel 内容模型 + View 结构原语。证据：源码确认；具体运行后果待新增复现。

当前链路：

- [`El::child` / `children`](../../crates/octara/src/view/element.rs) 对内容种类没有限制；
  `mount_el` 会把这些子视图挂到相同父节点。
- [`Kernel::insert_child`](../../crates/octara/src/kernel.rs) 也允许普通子节点进入文本节点。
- [`Kernel::sync_links`](../../crates/octara/src/kernel/rich.rs) 直接复制 `node.children`，按链接位置复用，
  给复用项设置 Link 角色、标签、值和 ID，并销毁超出链接数量的节点。
- `set_rich` 在 run 变化时调用 `sync_links`。没有区分哪些子节点来自应用，哪些来自内部文本链接。

因此，公开 API 允许的组合超出了内部管理器的假设。应用子节点可能在 run 变化时被当作链接处理
或被移除；这条静态路径不能由“只修按钮”消除。本轮没有新增代码复现，不能声称已观察到崩溃。

**建议契约：**

- 明确哪些内容拥有应用布局子节点，哪些是原子内容。普通组合由容器负责。
- 文本的 inline spans / links 继续属于文本系统；输入的编辑内容属于编辑器。
- 对不支持的应用子节点组合，在公开入口拒绝，并覆盖直接 Kernel 调用入口。
- 优先评估“文本/输入作为原子内容，容器负责组合”。只有出现明确需求，才考虑同时支持
  内部子节点和应用子节点的双重管理；不能为了保留一个容易误用的写法引入通用节点分区系统。
- 不能笼统禁止所有内容的子节点：图片、Canvas、Native 的装饰和叠层需求要分别列出契约；
  内部链接与公开 `.overlay` 也不能被误伤。

验收前提：动态富文本链接增加、删除、替换不会改写应用拥有的节点；非法组合要么被明确拒绝，
要么由定义好的组合规则管理，不能静默损坏。

### F2：有内容的节点不是天然可组合控件

优先级：高，依赖 F1。归属：View 原语 + kit。

[`button`](../../crates/octara-kit/src/lib.rs) 当前由 `interactive(text(label).role(Button))` 构成。
调用者可以继续 `.child(icon(...))`，但这并未把“按钮标题”和图标变成同行布局的两个普通内容项。
上一轮 Chat 真正出现过重叠，随后删除附加图标才恢复。

**建议：**按钮拥有一个交互根节点，标题或复合标签作为其内容。文本按钮只是常用构造方式。
控件外框与标签布局分开，文字、图标、badge 不各自拥有一套 press/focus 状态。

不能直接把所有 `button(IntoText)` 改成 `button(IntoElement)` 就认为问题解决，还要先决定：

- 动态标签如何绑定，继承哪些字体、颜色和省略策略；
- 复合标签的可访问名称来自哪里；
- 图标是否为装饰，复杂标签里哪些语义需要保留；
- `id`、焦点、按键、禁用状态和 press 归属哪个节点；
- `text_of(button_id)` 是节点自身文本查询，不应偷偷改成子树文本聚合以维持旧测试；
  应分清视觉内容查询与语义名称查询。

具体函数签名留到契约确定后选择。暂不引入新的 Button 状态机或第二套 Element trait 层级。

### F3：复合控件的语义名称不能由视觉布局隐式决定

优先级：高，和 F2 一起设计。归属：Kernel 语义投影 + 原语 + kit。

[`inspect/tree.rs`](../../crates/octara/src/inspect/tree.rs)、
[`kernel/a11y.rs`](../../crates/octara/src/kernel/a11y.rs) 和
`Kernel::find_by_name` 当前都主要使用“显式 label，否则文本节点自身文字”。
所以把按钮改成容器后，不能假定容器会自动获得内部文本的名称。

这不是现有所有容器都应自动聚合名称的证据。把帮助文字、badge、隐藏内容或嵌套控件一起拼接，
反而可能产生错误名称或重复播报。

**建议契约：**

- 交互根有清晰的名称来源。kit 的文本便捷构造可保证名称与动态标题一致；复合标签允许明确命名。
- Inspector、按名称查找和 AccessKit 对同一语义事实保持一致，优先共享解析规则，避免三个地方各猜一次。
- 装饰图标不参与名称；带独立语义的后代如何保留，需要按控件角色规定，不能一律隐藏整个子树。
- 视觉子节点重排不应改变根控件的目标身份或增加 Tab 停靠点。

Rune 的自定义标签显式保留按钮名称，值得借鉴。Exact 的“按钮内部标题在某宿主消失”的历史记录
提醒我们，结构可组合还必须有跨语义树的一致规则。参见[调研记录](../research/ui-composition-frameworks.md)。

### F4：App 共享资源入口尚未显式统一权限边界

优先级：高。归属：App/运行时与宿主启动。证据：源码确认入口差异；具体副作用待验证。

[`graph/execution.rs`](../../crates/octara/src/reactive/graph/execution.rs) 已统一执行阶段和操作权限。
但本轮检查的资源入口还存在另一组路径：

- View 的 `set_theme` 直接调用 AppState 的资源变更。
- `App::set_theme` 进入 App 上下文，但底层先替换 theme，再使窗口样式失效；这条路径未显式调用
  阶段权限政策。进入 App 上下文本身不等于获得写权限。
- `App::register_font`、`register_fallback_font`、`set_text_engine` 直接改变共享资源，然后通知窗口。
  它们与普通 Signal 写入口的准入方式不同。

来源：[`app.rs`](../../crates/octara/src/app.rs)、[`view/mod.rs`](../../crates/octara/src/view/mod.rs)。
不能据此直接声称当前 Chat 在派生计算中修改了主题，也不能声称已有崩溃。
要验证的是：这些入口从 Build/Derive/Observe/Cleanup、失败或关闭后的 App 被调用时，
是否会在拒绝前已经发生部分资源变化，是否遵守原有执行协议。

**建议：**把“首次初始化配置”和“运行期间资源变更”明确分开；后者在任何修改和内部可变借用之前，
复用统一准入政策。不要新增主题专用权限、异步初始化机制或一组公开 permit。

宿主层的具体摩擦也已确认：[`octara-shell::Options`](../../crates/octara-shell/src/lib.rs)
没有初始主题入口；宿主创建 App 后立即打开根窗口。Chat 用一个 `spawn` 设置静态初始主题。
应让初始主题在首个视图构建与测量之前生效，同时保留运行中的合法切换能力。
SwiftUI 的子树 environment 是参考机制，不是必须照搬的范围：当前证据不足以要求新增整套样式环境。

### F5：文本对齐缺的是共享布局表达，不只是样式函数

优先级：中。归属：Kernel 文本/样式、View 样式原语。

源码确认：[`TextStyle`](../../crates/octara/src/kernel/text.rs)、
[`Visual` / `Inherited`](../../crates/octara/src/kernel/style.rs) 没有文本对齐字段。
`items_center` 等容器对齐不能表达多行文本内部的对齐。

当前 [`rich.rs`](../../crates/octara/src/kernel/rich.rs) 分别缓存 text lines 和 glyph runs；
选择、链接、AccessKit 文本 run 几何依赖这些结果。若只在画字时平移，显示与交互会分离。

**建议契约：**对齐参与布局结果及相应缓存有效性，字形、光标、选择、链接命中与无障碍几何共同使用。
先区分逻辑 start/end 和物理 left/right；不能忽略 RTL 后把 API 名称定死。
测量自然宽度和在给定宽度内对齐也是不同问题。

验收必须包含多行、显式换行、容器缩放、富文本链接、选择与文本方向。
现有 Chat 的两行标题可以暂时用容器排列，不能把这个应用写法当成原语已经具备文本对齐的证据。

### F6：输入提示应与编辑值分离

优先级：中。归属：输入内容模型、展示/语义投影、View 输入原语；kit 提供默认外观。

源码确认：[`Input`](../../crates/octara/src/view/element.rs) 目前没有 placeholder/prompt 数据。
不能把提示写入 `.value`，那会污染选择、复制、撤销、提交和 Agent 读取。

**建议契约：**

- 编辑值为空且没有组合输入内容时展示提示；提示本身不成为编辑文档。
- 输入名称/label 与提示独立；提示不是稳定名称的替代品。
- 明确其裁剪、测量、样式和语义暴露方式，支持动态更新而不重建编辑器。
- 验证输入、清空、组合输入、撤销和 secure input 的边界。

SwiftUI 的 label / prompt / text 分离以及 Rune 的独立 placeholder 字段都支持这种划分。
借鉴的是状态职责，不能只照搬一个方法名。

### F7：数字表单首先应复用现有能力

优先级：中。归属：kit 和 Chat；本轮没有发现必须新增运行时原语的证据。

[`number_field`](../../crates/octara-kit/src/range.rs) 保留原始字符串，在 Enter/blur 规范化；
[`Model<T>`](../../crates/octara-kit/src/lib.rs) 接受 Signal 或 getter/setter；
[`field` / `FieldInfo`](../../crates/octara-kit/src/forms.rs) 已统一名称、帮助、required、invalid 与错误展示。
Chat 设置重复手写标签、错误和 `.invalid`，没有充分利用 `field`。

**保留：**编辑草稿与提交业务值分离；组件行为先于应用通知；读模型得到 setter 实际接受的值；
业务校验仍是普通 Rust。不能为了简短而把非法草稿和空值都折叠成 `Option<f64>::None`。

**需要明确：**`field` 当前会覆盖控件的 invalid，这是现状，不是无需评审的最终设计。
NumberField 默认把空串标为 invalid，Chat 的业务规则却允许空串表示模型默认值；
不能把所有覆盖都当成重复代码，也不能无条件 OR 所有校验结果。
`required` 不等于禁止编辑空字符串；草稿解析、业务提交资格和错误展示时机要分别定义。
number_field 的自动规范化、业务校验和点击 Save 时的失焦先后也要共同设计。
例如输入 `2.1` 后切换焦点会被范围规范化，这和“拒绝超范围值”是不同产品语义，文档必须说清。

优先把 Chat 改成同一份校验结果供字段和 Save 使用，再判断是否仍需 kit 便利 API。
暂不引入 Form 引擎、通用校验注册表或额外的数字状态原语。

### F8：诊断消费规则的问题不能误判成内核缺失

优先级：低。归属：验证工具和文档。

修正此前讨论：[`diagnostics.rs`](../../crates/octara/src/diagnostics.rs) 已把 `TEXT_TRUNCATED` 标为 Info；
[`inspect.rs`](../../crates/octara/src/inspect.rs) 的 `expect clean` 和 check 汇总已区分 Info 与警告/错误。
[`live_openrouter.py`](../../apps/chat/live_openrouter.py) 自行采用 ID 例外，才产生了另一套通过标准。

**建议：**验证脚本复用标准 clean 判定，保留完整信息供 Agent 阅读。
若某项产品验收明确不允许某控件省略，再加针对该需求的断言；不要因此新增第二个全局“允许截断”开关。
`COLLAPSED`、`OVERFLOW` 等实际几何问题不能被一并忽略。

## 4. 已有基础应该保留

| 机制 | 现有依据 | 结论 |
| --- | --- | --- |
| 作用域、执行阶段与依赖收集分离 | `graph/execution.rs`，既有内核收敛评审 | 保留；F4 是共享资源入口覆盖审查，不是推翻协议 |
| 组件事件层 + 应用回调 | `view/behavior.rs` 的顺序、消费和逐回调存活检查 | 保留，不新增事件总线或 kit 调度器 |
| IME 优先处理按键 | `app/keys.rs`，forms/interaction 集成测试 | 保留，不让 number_field、菜单、建议列表抢组合输入 |
| 有身份的编辑器与结构作用域 | 表单元数据变化保留 composition/selection/target 的测试 | 保留；验证变化不能靠重新挂载输入框实现 |
| 弹层与焦点机制 | choices/interaction 测试 | 保留，Dialog/Combobox 不各建一套焦点管理 |
| 增量列表与文本缓冲 | virtual/text_stream 测试，上一轮 Chat 验收 | 保留；本轮没有引入另一套结构 diff 的依据 |
| 统一语义来源 | Kernel → Inspector / AccessKit | 保留；完善名称和几何规则，不新增 Agent 镜像状态 |

这些是特定路径的证据，不是“整个内核已不存在问题”的证明。

## 5. 建议的后续顺序与完成标准

本表是后续计划，**本轮不实施**。

| 阶段 | 先解决什么 | 完成标准 |
| --- | --- | --- |
| A：底层契约 | F1 内容/子节点所有权，F4 共享资源准入 | 有针对性复现；非法组合早期拒绝或受明确规则管理；资源写入拒绝无部分副作用；合法初始化和切换成立 |
| B：支撑原语 | F3 名称来源，F5 文本几何，F6 输入提示 | Inspector/AccessKit/命中一致；提示不影响真实编辑值；布局与缓存随相关状态正确更新 |
| C：kit 组合 | F2 复合按钮，F7 表单组合 | 图标/文字正确布局，一个交互根和焦点；编辑草稿不丢失；校验与提交一致；不新增内核任务/状态系统 |
| D：应用与工具 | Chat 接入，F8 诊断消费 | 删除已被基础能力替代的绕行代码；复用 clean 判定；现有业务语义和真实窗口结果保持 |

各阶段先设计接口与失败行为，再实现。测试要覆盖契约，而不是只复刻实现细节。
未来真实窗口验收需明确输入路线；已有 Inspector 输入验证不能冒充 OS 输入或跨平台 IME 证明。

明确不做：VM、新执行引擎、通用 capability 框架、另一套表单状态系统、按控件各自实现生命周期、
