# 从基础机制到组件树的架构评审

日期：2026-11-17。已提交基线：`d5619e8`。
状态：评审与设计建议，不是已完成的 API 迁移。
工作区中的 D2a 按钮、Chat 和文档改动是待评审草案，本轮保留但不继续扩展。

## 总体结论

开发者应通过组件接收参数和内容、返回 UI 树来构建界面。底层提供少量可组合的
内容节点、响应式状态和通用交互机制；ui-kit 在这些机制之上组合行为、语义和外观。
一个新组件通常只应增加组件实现，不应增加内核节点、挂载协议或公开原语。

当前 core 已有 `El`、`View`、`IntoElement`、fragment、动态分支和 keyed 挂载，
不是缺少组件树。主要缺口是 kit 没有一致地表达内容、配置目标和内容构建时机。
因此，应先收敛组合契约，再改组件 API，而不是继续增加 `*_with_content` 一类入口。

这里的组件树首先是开发者组织代码的模型。组件可以返回一个节点、多个兄弟节点或空内容，
不要求每个组件都产生布局盒或新的运行时对象。保留 Rust + Signals 和现有 retained tree；
本轮没有引入 VM、通用 diff 引擎或第二棵运行时组件树的依据。

## 自底向上的审查

下表区分职责，不要求每一行对应一个新 crate。现有包依赖由 `tools/check_layers.py` 检查。

| 层次 | 已有机制与证据 | 评审结论 |
| --- | --- | --- |
| 基础值与协议 | `octara-primitives`；几何、样式值、输入和语义数据 | 保留独立性；不要加入 Button、Field 等组件概念，也不要把所有公开数据类型统称为开发者原语 |
| 响应式与执行生命周期 | core 的 Signals、owner、执行权限、取消和释放边界 | 继续复用；组件组合不需要新的调度器或每组件执行协议。本轮是边界审查，不是重新证明所有并发契约 |
| 文档与编辑状态 | kernel 节点、编辑提案/接受、选择与历史；R1–R3 的验证 | 保持事实的单一所有者；kit 不保存编辑器副本。无需新增 Button/Dialog 内核种类 |
| 文本、布局与呈现 | `octara-text`、kernel 布局、`octara-render`；R2 的显式几何结算 | 复用同一几何与呈现事实；组件不自行推算输入光标或弹层锚点。渲染器和宿主接口不等同于写组件的日常接口 |
| UI 构建与挂载 | `view/mod.rs` 的一次性 `View`、`IntoElement`、fragment、show、keyed | 能力已有；需要明确内容值与延迟工厂、构建上下文、身份保持的共同契约，挂载回调继续私有 |
| 交互与语义 | `El::behavior`、事件顺序、焦点、动作资格、显式 label、overlay | 复用；需要明确单动作内容与独立交互后代的边界。隐藏 AX 内容不等于禁用交互 |
| ui-kit | 普通函数组合 El/View；按钮、field、popover、choices | 主要重构面：统一内容传入方式，明确配置落点，删除重复派生数据；组件差异仍由组件政策表达 |
| 应用与 Agent | Chat、Inspector、AX、布局诊断、目标身份 | 应用只管理业务状态；组件结构调整必须保留动作目标，且诊断仍能定位实际出问题的视觉内容 |

依赖方向继续向下。当前 `octara` 同时包含 runtime、kernel、view 并不自动构成反向依赖；
应检查它们调用与事实所有权的边界，而不是为了层数好看继续拆包。

## 当前需要解决的具体问题

### 1. 内容组合有基础，但 kit 入口不一致

`view/mod.rs` 已允许 `El`、`View` 和字符串通过 `IntoElement` 组合，fragment 无需多余容器。
`structure.rs::collapsible` 已分别接收 header 内容和延迟构建的正文。
因此不能把“引入 children”当作一项全新的内核能力。

已提交的 button 是带 Button role 的文本叶子；未提交草案改为动作容器，方向合理，
但 `button_with_content(name, content: El)` 又引入专门函数，而且内容仅限 El。
应先确定一个组件的普通内容参数如何接受现有 View/fragment，再决定便捷构造写法。
不应为图标、富文本、加载状态分别扩充一组底层原语。

### 2. 返回 El 不代表所有配置都作用于真实控件

`forms.rs::field` 正确地把名称、描述和验证属性放到传入 control 上，但返回的是外层容器。
用户随后给返回值加 disabled 或 handler，不能假设它会转发到内部输入。
`structure.rs` 的 collapsible、split 同样具有外层容器和内部交互节点。
相对地，popover 返回传入 trigger，目标含义较明确。

应明确区分容器布局配置与控件行为配置。简单单动作组件可把动作根作为配置对象；
复合组件用明确的参数或小型 builder 配置 control、label、container。
不引入通用 Parts 注册表，也不自动把所有 El 方法转发给某个内部节点。

### 3. 任意 children 与单动作语义不能混为一谈

按钮草案把整个内容子树设为 `a11y_hidden`，仅靠文档要求不要嵌入独立控件。
这不保证后代无法获得焦点或处理事件，因此还不是完整契约。

需要明确：按钮的内容是同一动作的呈现；独立输入或按钮应作为兄弟动作组织。
后续实现须选择可验证的约束方式，覆盖嵌套动作和可聚焦后代；不能把从 AX 隐藏当作验证。
这不意味着所有容器都禁止交互后代，也不意味着必须新建一套内容类型系统。

### 4. 内容构建时机必须先于 API 定型

已经构建的 `El/View` 与延迟调用的内容工厂，具有不同的构建时机。
show、overlay 等按挂载需求调用工厂，不能直接推断为普通值参数的上下文语义。
需要验证 provider 的读取位置、owner 归属、取消/释放以及重新挂载行为。

普通静态内容优先传现有内容值；确实需要延迟或重建的边界才使用工厂。
不把所有 children 强制改成闭包，也不公开 Mount 或要求 View 可克隆。
这是待补的明确契约与验证，不是在本轮认定已有泄漏或生命周期故障。

### 5. 派生数据与业务状态要分别处理

Combobox/PopupList 内有由 items 派生、再同步进 StateList 的选项数据。
应审查是否可直接由 keyed 集合与派生值表达，减少镜像维护；删除前必须验证重排、过滤、
移除和禁用期间的身份与导航行为。

selected、query、open、active 则表达不同事实，不能因为都在一个组件里就合成单一状态。
Menu 命令、输入建议和选择器也不能只因外观相似就合并交互政策。

### 6. 语义目标与视觉诊断位置都要保留

按钮由文本叶子变为容器后，布局诊断可能落在内部文本，而动作 ID 留在根上。
草案迁移已暴露这个差异，并通过给内部标签显式 ID 调整相关断言。
它说明需要明确诊断如何指向实际内容及其组件位置，不能只把既有断言改到通过。

动作身份、集合 key、用户给出的查找 ID 和诊断位置不是同一个概念。
不应为了合并它们新增全局 ID 体系，也不应通过忽略内部文本诊断隐藏真实截断。

## 从参考框架选择性借鉴

本地参考版本固定如下，没有将其描述为已联网验证的最新提交：

- Rune `3686e94ae09545fd5f2a61e22aabfbeba1cd896f`，
  `crates/rune-kit/src/actions.rs::Button::label_with`：视觉内容可替换，可访问名称单独保留。
  借鉴这条契约，不必复制 Kit/Acts/Label 整套类型体系。
- Exact `08c889a9de21a30b7c3b308422fc588cf1a480d3`，
  `docs/contract-for-humans.md` 的 slot：组件包装调用者内容，内容保留调用者词法上下文和 providers。
  它明确是一个 slot，而非任意命名插槽和 render-function 系统。
  借鉴内容传递与上下文语义的明确性，不能直接宣称 Octara 当前已经具有完全相同的行为。
- Exact 同版本 `semantics/corpus/edge/tap-child-of-button.contract`：
  按钮后代点击属于需要单独验证的契约。本轮阅读语义样例，没有运行 Exact 验证套件。
- React 的 [props 与 children](https://react.dev/learn/passing-props-to-a-component)
  展示了组件包装其他组件的直接表达；[状态身份](https://react.dev/learn/preserving-and-resetting-state)
  明确了树中位置、类型和 key 对状态保持的影响。借鉴组合表达和明确身份规则，
  不因此引入 React 的渲染执行方式；Octara 仍需以自己的挂载与 Signals 语义定义身份。

## 重构前必须定下的四条契约

1. **内容契约**：普通内容用现有 UI 描述组合，支持空内容和兄弟内容；需要延迟的边界明确使用工厂。
   明确内容构建处与挂载处分别决定哪些上下文，不凭函数签名猜测 provider/owner 语义。
2. **配置契约**：每个参数或链式方法必须有明确目标；复合组件不能让外层容器冒充内部控件。
3. **身份契约**：视觉内容和样式变化不重建动作根或编辑器；需要重建的动态分支遵循已有 key/region 规则。
4. **行为契约**：沿用统一事件顺序和权限检查；明确内容后代与独立动作、IME 与建议导航之间的政策边界。

先用 Button 和 Field 两个不同复杂度的组件推演这四条契约。
Button 需要名称、外观与内容；Field 需要 label、实际 control 和辅助信息。
这些是组件参数，不是要求新增同名内核原语。具体 Rust 签名待两者的调用样例一起评审，
不提前锁定函数、props struct 或 builder 中的某一种形式。

## 合并、重构与删除范围

| 处理 | 范围 |
| --- | --- |
| 保留 | 基础包方向、Signals、统一执行权限、编辑所有权、既有 View/挂载、焦点/语义/布局机制 |
| 统一 | 组件内容传入、配置目标、构建时机与身份的说明及验证 |
| 重构 | Button 的容器内容模型；Field 等复合组件的明确配置；必要的内容语义校验 |
| 有证据后删除 | 选项派生镜像、误导性配置转发、被统一构造完全替代的专用入口 |
| 不引入 | VM、另一套事件或生命周期系统、全局 Parts 注册表、每个 kit 组件一个内核节点 |

`primary_button` 等便捷函数不因数量本身就必须删除：如果只是同一构造的薄外观封装，
可以保留。删除对象是重复机制和难以组合的独立路径，而不是机械减少函数数量。

## 推进顺序与完成标准

1. 评审 Button 与 Field 的调用样例及上述四条契约，再恢复 D2 实现。
2. 以这两个组件完成纵向迁移，替换当前按钮草案及其未提交的文档/skill 描述，删除被替代入口。
3. 再推进动态选项身份与派生数据收敛，最后统一外观配置和 Chat 集成。

验收至少覆盖：

- 不依赖 kit 的组合能力仍成立，不新增 Button/Field 内核节点。
- 普通文字、自定义视觉内容、fragment 使用一致的内容模型；不依赖专门构造家族。
- 单动作内容的点击、键盘、AX 和 Agent 路径一致；非法独立交互后代有明确处理与验证。
- Field 的名称、disabled、错误和事件配置作用于真实 control；容器样式不改变输入身份。
- 内容值与延迟工厂的 provider、owner、重新挂载及释放语义有针对性验证。
- 视觉内容变化保留动作目标、焦点、输入选择与组合状态；诊断可定位实际视觉问题。
- 调用方、文档、vocab/skill 同步迁移；完整回归、格式、Clippy 和依赖分层检查通过。

历史 D1 的 926 项测试通过只证明其记录的场景，不是本轮草案的验收结果。
本轮只做源码/参考资料审查和文档更新。真实 OS 输入、窗口截图与辅助技术体验继续单列，
按用户安排后续执行，不用 headless 结果代替。
