# 面向 Agent 的 UI 函数组合架构

日期：2026-11-17。状态：方案已批准，按文末收敛顺序实施；各阶段单独验证和提交，未完成项不视为已验收。
框架首先面向 AI 编写、修改和验证应用，默认采用 **Rune 式普通 Rust 函数组合**。
不再将“组件声明宏为每次调用创建实例”作为并列主路线，也不按人工手写代码最少来选择抽象。
函数的输入、响应式更新、运行时所有权和操作反馈应可追溯、可验证。
具体状态构造、context 范围和热重载契约仍需区分性验证；函数组合不等于已批准匿名状态重置。
依据与反例见[机制调研](../research/ui-composition-mechanisms.md)，特别是第 10、11 节。
依据：[自底向上审查](bottom-up-api-review.md)、[组件树审查](component-tree-review.md)。
保留 Rust、Signals、retained tree、现有执行权限和编辑协议。不保留被替代接口的兼容路径。
当前 D2a 按钮草案暂停，不能作为本方案已经落地的证据。
kit 不再是应用必须经过的架构层。本文件第 9 节给出职责去向；先消除重复所有权和协议，
再决定包的归属，不以删除 `octara-kit` 包作为本轮验收条件。

## 1. 设计目标

让 AI 通过普通函数表达内容、排列、语义与交互，并能根据编译结果、实际节点、诊断和输入反馈
完成局部修改。评价的是生成 → 编译 → 运行 → 检查 → 操作 → 修复能否闭合。
不以宏是否像手写 JSX、API 名称数量或按键次数作为主要标准。
框架负责身份、编辑、执行资格和资源释放；这些保证不能依赖每次生成应用时由 AI 重新补齐。

本轮保留 Signals 图算法与 retained tree，重新设计 UI 组合及其状态构造、所有权入口。
局部状态新分配是独立候选，会改变 state 构造和恢复契约；它不是采用函数组合的前提。
原有“基础原语 + Core 通用能力”分类不再作为强制公开层级；需要公开的能力按实际用途提供，
没有额外语义的透传层删除。现有 crate 方向保持，不先增加包。

```text
应用的普通 Rust 函数（业务、UI 结构与外观）
           ↓
Octara UI 函数：内容描述、节点属性、语义交互、动态结构
           ↓
现有挂载与执行协调
      ↙            ↘
 Signals        retained tree
                  ↓
        编辑、布局、语义与绘制输出
```

图中的职责不是要求四个新 trait 或四个公开服务对象。
组件示例和可复用配方可以供 AI 阅读或直接复用，不作为应用必须经过的中间层。

## 2. 推荐的作者模型

### 普通函数是默认组件形式

函数接收普通 Rust 数据、Signal/ReadSignal、内容和回调，返回 El 或 View。
自定义卡片、Chat 输入区与 kit 控件使用同一组合方式，不要求实现 Component trait、注册组件类型、
声明 props schema 或使用决定生命周期的宏。参数允许普通 struct，不能强制所有组件只有同一个签名。

函数只在实际构建时执行；之后状态变化更新读取它的绑定。采用 Rune 的组合方式，保留 Octara 的
Signals 更新机制，不引入全量 view 重跑与手写版本缓存的第二条默认路径。

优先通过参数传入状态和行为，使 AI 能在函数签名与调用处定位依赖；就近的临时状态也可以保留，
其 owner 必须来自明确的运行时边界。函数调用本身不自动创建 scope。
条件分支、列表行、弹层、窗口和有独立上下文需求的内容范围继续管理存亡。
任务、watch、cleanup 跟随所属 owner，不能因函数返回或任意布局包装而改变归属。

当前命名 state 可在这些边界或 App 初始化中创建，再传给普通函数。是否让局部状态默认新分配、
如何跨重载恢复，是后续独立契约；不能只为证明函数组合可行就重做 Signals 对外接口。
同样，不先为每个函数增加 scoped 包装来绕过命名冲突。

保留 Agent 需要的函数来源、调用点和节点来源；来源注解只负责溯源，不改变正文执行时机和 owner。
是否调整 `#[component]` 的名称由这一职责决定，不能为少一个宏而丢掉定位信息。

### 一个内容模型，不强行一个万能类型

保留两种现有职责：可配置的元素描述 El，以及可挂载的内容描述 View。
El 可转换为 View；View 可以是元素、兄弟内容、空内容或动态区域，不因此增加容器。
各组件的普通内容参数统一接受这一转换，不再每个组件规定专用 Content/Children trait。

容器接受 children；文本、输入、图片、画布与宿主内容有各自的数据接口。
文字与图标仍可组合在容器内。组件不需要通过修改原子节点种类来获得 children。
统一 El 暂可保留内容适用性诊断；不为每种节点建立一套复杂泛型状态机。

普通内容是一次性值。只有条件分支、列表行、上下文范围、弹层等需要延迟创建或重新创建时，
才接收工厂。重复呈现需要每次产生新描述，不能克隆有状态 View 或重复挂载同一描述。

### 候选基线：上下文按实际构建处解析

选择以下规则，不复制 Exact 的编译期 lexical provider 机制：

- Rust 闭包捕获的变量照常属于词法环境。
- `use_context` 在调用发生时读取当前 scope 的 provider。
- 延迟工厂在新的挂载 scope 中执行；该 scope 的父级是拥有这个动态区域的逻辑 scope。
- 普通函数不会新建 provider 边界；局部 provider 应绑定内容范围与工厂，复用现有 scope 实现隔离。
- 预先构建的内容不因被插入另一个容器而重新运行其构建代码或重新读取 provider。
- provider 替换不自动让已有读取响应更新；动态上下文继续传 Signal。

因此，提前读取并捕获一个 context 值，和在延迟工厂内调用 use_context 是有意不同的操作。
当前裸 provide 修改 active scope，不能把它解释为只影响当前函数返回的内容。
范围式 provider 是待验证的替代入口，不新增第二套上下文运行时。
来源标记、Rust 捕获环境、挂载 owner 不混成一个可随意恢复的执行上下文。
内容的 Signal 依赖由闭包实际读取决定；挂载绑定、任务与事件的生存期由实际 owner 管理。
退休后继续拒绝调用与发布，释放仍沿用原协议。

## 3. 属性与交互：通用，但不是任意拼装

### 属性只配置明确对象

尺寸、颜色、间距、显示状态等修改当前元素；同类属性按现有覆盖规则解析。
row/col 是容器布局便利入口，不删除。普通 style 链不隐式产生包装节点。
增加结构应通过明确的容器或组件表达；向后代传递默认值须有明确的继承规则。

复合组件接收实际 control，control 的事件、禁用和值在 control 上配置。
组件返回外层布局内容并不承诺代理内部控件。Field 的 label/help/error 是内容与关系，
不要求新增 Field 内核类型或一个能查找所有内部部件的注册表。

### 基本激活作为一致契约

目前 on_press 已汇合指针、键盘和辅助技术入口，不能再建立第二套动作分发器。
需要收敛的是 role、焦点资格、禁用、激活和子内容约束的声明：提供一个普通的无外观
按钮构造入口，返回既有容器并复用行为和资格检查。它是普通组合函数，不是新的 Button 内核节点。
优先从入口就确定动作根，再接收任意合规的视觉内容，避免向任意已有子树注入语义属性。
具体签名待样例验证；不先发明通用 Behavior DSL。

该入口应保证：

- 根节点拥有名称与动作；内容点击归同一动作；键盘、AX、Agent 走同一资格判断。
- 动态 disabled 阻止激活；焦点与清理使用已有机制。
- 纯呈现子内容不重复成为无障碍动作；禁止独立交互后代有可定位诊断。
- 检查动态插入与可聚焦后代，不能只检查初始静态树，更不能只设置 a11y_hidden。

语义 role 本身仍不自动产生任意交互行为。其他控件是否也需要这种组合入口，
由真实调用重复证明，不一次性生成 Toggle/Select/Range 等整套新原语。
低层事件与语义属性保留给自定义控件作者使用，采用同一事件协议。

### 动态结构与展示不拆出更多对象

保留条件区域、keyed 列表和虚拟列表的不同语义，共享现有挂载/退休机制。
普通列表优先使用 keyed 快照；有增量需求再选 ReadList。不要为了渲染快照先同步进 StateList。

弹层仍是逻辑所有者持有的动态内容，渲染位置可以在窗口 overlay 层；呈现父节点不重定义
context 和状态父级。关闭释放面板内容，锚点卸载使面板失效；重新打开创建新的面板实例。
模态、恢复焦点、建议列表不抢焦点是显式政策，不能把所有 overlay 自动变成 Dialog。
位置由统一布局计算，kit 不复制锚点几何和编辑状态。

## 4. 四个场景反推能力

以下是结构推演，不是已实现 Rust API，也不新增需要编译的示例。

### A. 卡片 / 容器组合

```text
Card(content) = 容器(背景、边距、圆角，children = content)
页面 = 列容器[Text(标题), Card(行容器[Icon, Text])]
```

Card 是普通函数，无 scope、无独立节点种类。内容允许 fragment，函数不额外增加包装。
只有作者写出的卡片容器产生布局节点。证明普通包装不需要组件协议对象。

### B. 自定义按钮

```text
动作根 = 无外观按钮(名称、禁用、回调)
内容   = 行容器[Icon, 动态 Text]
kit    = 为动作根提供默认尺寸、颜色及交互状态样式
```

自定义外观与 kit 使用相同基础装配。加载图标、计数、富文本都是内容，
不增加 button_with_icon/button_with_content 等独立机制。
内容更新不重建动作根；嵌入独立输入或按钮要诊断，不悄悄隐藏仍可操作的后代。

### C. 相同函数，两份独立状态

```text
counter(count: Signal<i32>) = 普通组件树，事件更新 count
left  = 在所属生命周期边界创建的状态
right = 在所属生命周期边界创建的另一份状态
页面 = 行容器[counter(left), counter(right)]
```

两个值相互独立，普通函数包装不新增状态层。需要独立卸载时，分别置于动态边界并在那里创建状态；
若主动把状态放到更长寿命的模型中，隐藏 UI 不销毁该业务状态。
动态行重排保留该行 scope 与节点；跨所有者迁移不承诺自动保留状态。
不把查找控件的 id 当作运行时 scope key 自动复用。
这已经能采用函数组合；函数内直接创建匿名局部状态的便利性另见研究候选 C。

### D. 中文输入与建议面板

```text
suggestion_input(业务值、query、open、active、接受回调) =
    editor + editor 的锚定动态内容工厂(keyed 建议行)
```

editor 始终挂载；候选数据变化只更新面板行。IME、selection、undo 留在既有编辑所有者中。
建议键盘政策明确让位于 composition，指针建议不抢编辑焦点，接受建议是正常业务写入。
面板关闭取消其工作并拒绝迟到事件，窗口缩放只更新统一几何。
这里需要输入、锚定展示和动态内容，不需要新的 Combobox 内核节点。

## 5. 现有抽象的处置

| 现有机制 | 目标处理 |
| --- | --- |
| 独立 ui-kit 目标层 | 建议取消，按第 9 节拆分职责；不把整个包改名搬进 core |
| Signals、运行时权限、取消与释放、retained tree | 保留实现与验证契约 |
| 原子编辑、焦点/输入路由、统一语义和布局 | 保留，组合层调用同一机制 |
| El / View / IntoElement | 保留职责，统一所有普通内容入口；不继续扩张万能 El 转发 |
| component / component_keyed | 不再作为普通组件的必经路径；确认独立延迟/恢复用途后合并或删除，保留实际 owner 机制 |
| 只记录来源的 component 宏 | 保留溯源能力，名称与职责对齐；不扩展成强制生命周期宏 |
| role/focusable/on_press 等零散动作装配 | 保留底层属性，新增或提升一个共用的无外观装配函数，删除 kit 的重复装配 |
| Behavior | 继续复用已有有序回调合并，不新增调度系统 |
| button_with_content 草案 | 被统一内容构造替代，不继续扩展专用构造家族 |
| 复合组件的隐式属性转发预期 | 删除；control 参数明确，容器配置明确 |
| Combobox/PopupList 选项镜像 | 迁移到现有 keyed 快照后删除同步状态与算法 |
| StateList/TextBuffer、原生互操作和绘图 | 作为按场景使用的能力，不算最小组合模型的必修接口 |
| core 中可由普通组合表达的透传层 | 合并或删除，不按目录层数强制经过 |

## 6. 参考机制与不采用的部分

参考证据和固定提交详见[源码交叉审查](bottom-up-api-review.md#rune--exact-源码交叉审查)。
Rune 提供普通数据/函数/El 的直接组合经验；保留我们的 Signals，不移植 App S + Tx 模型。
Exact 提供组件展开与实例归属分离的经验；不引入 compiler plan，也不暗中承诺 lexical provider。
SwiftUI 的统一视图组合、可替换按钮 label 和明确身份适合参考；
不移植每个 modifier 包装新 View 的类型表达。React 的 props/children 用于检验组合表达，
不引入按组件函数重跑的更新模型。

## 7. 实施顺序与停止条件

1. **先定调用契约**：按普通函数主路线推演上述四个场景和 Chat 的实际函数签名。
   明确参数依赖、配置对象、内容工厂、状态和 context 归属，不再比较强制组件宏的手写便利性。
   保留命名状态与新分配的差异说明；热重载保证未裁定前不删除旧恢复路径。暂不修改生产接口。
2. **组合层纵向迁移**：普通内容入口、状态边界及来源记录一起迁移，删除旧路径；补双实例、
   provider 构建时机、动态内容释放与身份测试。此阶段不改变编辑协议。
3. **统一交互机制**：应用的自定义外观与基础语义函数共用动作、焦点、编辑协议，完成动态嵌套检查；
   用字段与建议组合检查配置目标，不引入通用 Parts 系统。若第 9 节方案采纳，同步拆除 kit 职责。
4. **动态内容与应用**：删除选项镜像，迁移建议面板与 Chat；确定 Markdown 等独立能力的归属后，
   再决定删除 kit 包。统一文档、vocab 和 skill，不能先删包再留下不可构建的应用。

每阶段验证并提交；不把旧草案混入已完成阶段。真实窗口按用户安排单独验证。
如果只能通过增加新的节点种类、并行 owner 或组件私有编辑器完成四个场景，应停止并重新评审。

完成标准：四个场景使用同一内容模型；作者能预测状态和 context 归属；kit 无私有内核特权；
节点/编辑身份及迟到事件资格不退化；旧路径实际删除；完整回归、Clippy、分层与 skill 检查通过。
“接口少了”与“能渲染截图”都不能单独作为验收依据。

## 8. Agent-first 的额外验收条件

目标是给 AI 一手上下文和反馈，继续使用正常的编辑、构建和运行循环，不引入自我改进引擎。
本框架已有的 [Agent context](agent-context.md) 和 Inspector 是基础，不能另建平行的语义树或状态镜像。

| AI 要完成的工作 | 框架应提供的事实 | 当前评审边界 |
| --- | --- | --- |
| 找到需要修改的函数 | 实际节点的源码位置、构建函数/调用点 | Inspector 已有来源字段；重构须保留，不能把来源当 owner |
| 确认参数影响哪个对象 | 明确的控件参数、内容参数与属性目标 | 删除隐式转发；不承诺已能追踪所有属性来源 |
| 判断变化是否更新 UI | Signal/绑定契约、冻结读取等结构化诊断 | 复用现有追踪与诊断；不要求所有业务值实现 Serialize/Debug |
| 操作真实控件并决定下一步 | 当前动作能力、有效 target、delivered/refused/unknown 与 pending | 保留过期校验与输入分阶段反馈，不把输入送达等同于业务完成 |
| 验证局部改动 | 同一实现上的场景、语义/几何检查、截图和真实窗口证据 | headless 不替代 OS IME 验证；未验证项明确报告 |

可检查的场景包括：替换按钮视觉内容后动作目标是否保留；抽取 card 函数后 owner 是否不变；
删除列表行后迟到回调是否失效；输入建议更新后 IME/选择是否继续；诊断能否定位实际出错的构建点。
这些事实比计算 API 数量更有用。完整模型能让 AI 正确生成和局部修改，比让某一段示例更短优先。

## 9. 是否取消独立 ui-kit 层

建议取消它作为目标架构中的独立产品组件层。当前 `octara-kit` 本来就是可选的：核心没有依赖它，
已有无 kit 的 foundation 用例。因而仅删除包名不会简化内核；需要减少独立规则、重复状态和固定外观体系。
本节是对用户问题的设计建议，尚未执行删除或迁移。

按现有源码拆分，而不把整个目录原样移入 core：

| 当前内容 | 建议去向 | 迁移边界 |
| --- | --- | --- |
| primary/ghost 按钮外观、chip、callout、列表标题、默认间距和尺寸 | 应用普通函数或带验证场景的参考配方 | 名称、角色、焦点等交互要求仍使用统一框架能力 |
| 按钮激活、值绑定、数值步进与动作资格 | 必要的通用交互函数/既有协议 | 没有证据需要增加 Button/Slider 内核节点；不把默认皮肤一起下沉 |
| Dialog/Popover、菜单、选择列表的通用输入和焦点规则 | 复用 overlay、modal、命令、焦点及编辑边界，归并确有重复的公共机制 | 保留 Escape、焦点恢复、IME 优先和接受/拒绝结果；不能只保留几何外壳 |
| Combobox、输入建议、Tabs、Field 等复合 UI | 普通组合函数或经过验证的配方；保留有实际复用价值的无外观函数 | 不建立组件注册表、强制组件状态类型家族或 Parts 协议；业务政策留在调用者 |
| options/rows 等重复可写镜像 | 用现有 keyed 快照/派生输入替换后删除 | 仍保留稳定 key、活动项与已选值的差别及重复 key 处理 |
| `Model<T>` 的 getter/setter 适配 | 先验证由值输入与提案回调表达的调用方；无剩余用途才删 | 它支持拒绝/归一化写入，不能用直接 Signal::set 替换全部自定义 setter |
| 流式 Markdown | 按需内容能力，另定应用模块或可选扩展的归属 | 涉及解析、增量呈现和选择；不因删 kit 塞进 kernel，也不在此时新拆一串包 |

不要求 AI 每次重新设计一套键盘和 IME 协议。交互机制仍是同一份受测试的实现，
AI 主要组合内容、样式、业务值与回调。参考配方的可复制部分应是装配和外观，
不能把一份复杂交互状态机复制到每个应用，再宣称框架已经精简。

普通 Rust 状态结构仍然可用，但不要求每个控件新增 `XxxState`、控制器或构造协议。
是否传一个 Signal、几个参数或业务结构由具体函数需要决定。前述函数组合方向不自动推出
一整套公共控件状态类型；这会再次扩大我们希望收敛的抽象面。

### 从实际调用检查删减是否成立

- Chat 的 `sidebar()`、`composer()`、`transcript(thread)` 当前通过 `chat()`/`listing()` 取得 context。
  可先推演为 `sidebar(&Chat, listing)`、`composer(&Chat)`、`transcript(&Chat, thread)`。
  闭包复制 Signal 或克隆现有 Chat 句柄，不捕获短期的 `&Chat`。无需引入统一 Props/Action 类型。
- `Chat::new` 同时注册请求清理；显式传参不改变该资源根的寿命，不能为了删组件包装就让请求逃逸到 App 根。
- `card(content: impl IntoElement) -> El` 与 `counter(id, Signal<usize>) -> El` 已可用现有公开接口实现。
  `El` 配置实际节点；`View` 组合空内容、fragment 或延迟结构，不给它增加猜测目标的 `.disabled()` 转发。
- 当前 `field` 接收实际 control，返回外层容器；`popup_list` 返回 View。这是复合控件配置仍须解决的
  实际边界。取消 kit 后，输入的禁用、名称与回调应在实际 editor 上配置，再组合标签、提示和弹层，
  不通过一个万能 Field 对任意后代猜测转发。
- 普通闭包已经能表达延迟内容；来源宏只用于 Agent 定位。不存在增加组件生命周期宏的前置条件。

下一步应先做逐项保留/迁移/删除清单和一条无 kit 的 Chat 纵向调用草图。
涉及复杂交互时对照现有行为测试；所有使用点与文档迁移后才移除 crate 与依赖。
当前仍处于设计讨论，生产实现保持原样。

## 10. 本轮已取得的验证证据

用当前公开 core API 构建了临时、无 `octara-kit` 依赖的 Rust 探针，复用仓库构建缓存。
**4 个 headless 检查通过**：共享/独立状态与来源信息；分支工厂的创建/清理/重新挂载；
输入提案与接受值的回调顺序及编辑节点身份；keyed 快照重排/删除/重建。
这些函数没有使用 `component(...)`/`component_keyed(...)`；保留的 `#[component]` 只记录来源。

结果支持现有机制能够承载函数组合，不证明新的 kit 拆分已经完成，也不覆盖复杂建议控件全部键盘规则、
跨重载状态恢复或真实 OS IME。本轮未改生产源码、未运行全工作区回归、未进行真实窗口验收。
源码与复现说明见[调研记录的验证附录](../research/ui-composition-mechanisms.md#12-普通函数组合的隔离验证)。


## 11. 已批准的自底向上收敛方案

依据：[Rune 执行架构研究](../research/rune-execution-architecture.md)。普通函数负责组合，
Signals 负责失效，运行时统一承担交互与生命周期。Signals 与 retained tree 是并列基础机制，
挂载和窗口协调连接二者；不新增超级内核、VM、手工 version 缓存或第二套组件运行时。

| 层 | 保留 | 合并/收敛 | 删除/退出默认路径 |
| --- | --- | --- | --- |
| 基础值与协议 | 几何、绘制、输入、布局值、身份 | 同概念共享类型 | 无额外语义的透传层 |
| Signals/生命周期 | Signal、memo、watch、untrack、owner、取消与释放 | 统一注册和执行权限 | 可写派生镜像、第二套失效协议 |
| retained tree | 节点身份、编辑、布局、语义、失效分类 | 节点事实的唯一所有者 | 控件自建编辑器/名称/焦点副本 |
| 执行协调 | 输入、反馈收敛、发布 | 通过内部类型/借用限制阶段能力 | 绕开执行资格的捷径 |
| UI 组合 | 普通函数、El/View、绑定、动态内容 | 内容转换和内部 owner 协议 | 来源与生命周期混称 component 的旧入口 |
| 交互 | 激活、焦点、键盘、IME、模态、滚动 | 共享行为与执行资格 | 应用重复实现输入状态机 |
| 组合库/外观 | 有价值的复合交互和普通样式函数 | 自定义内容与默认外观复用行为 | 选项镜像、同步 watch、纯透传组件层 |
| Agent | 操作、语义、截图、诊断、计数 | 产品执行链和身份协议 | 独立模拟业务行为的工具实现 |

StateList/ReadList、TextBuffer 保留为增量场景能力，不是普通列表/文本的必经路径。
El 是可配置元素，View 是可挂载内容，保留不同职责；show/keyed/each/virtual_each 共用
挂载、身份、释放机制，不强制压缩为一个复杂接口。row/col 是便利函数，不是重复内核。

来源注解不改变执行时机或 owner。普通函数不自动隔离命名 state；独立内容范围按需拥有
生命周期，条件分支、列表行和弹层共用内部协议。替代 component/component_keyed 时必须
同时验证多实例、命名状态、provider、清理和热重载；不保留旧名兼容别名。

执行阶段审查先找真实越界：测量是否调用业务、重试是否发布副作用、未收敛结果是否被
当作稳定结果。已有边界正确时保留；不为了照搬 Rune 再构建整棵候选树。

### 顺序与阶段门槛

1. **选项数据。** 删除 Combobox/PopupList 可写选项镜像，保留协调 open/query/active/selected、
   导航、reveal 和 IME。验证重排/更新/移除、重复 key、拒绝选择、过期目标和编辑身份。
2. **构建/owner/来源。** 普通函数为默认组件，来源与范围分别命名和实现；替换旧入口并迁移
   调用方、CLI/skill/文档。验证同函数双实例、上下文范围、动态销毁、热重载及诊断来源。
3. **执行阶段。** 根据实际审查结果收紧测量/反馈/发布能力；验证重试、跨窗口、失败和
   用户回调边界。没有证据的重写不实施，记录保留依据。
4. **组合库和公开面。** 复合行为继续复用底层协议，外观归普通函数/配方；精简 prelude，
   移除纯透传和重复路径。验证自定义外观的键盘/IME/禁用/语义行为及 Chat 调用体验。

每阶段独立提交实现、验证和文档；每阶段不必新增 crate 或公开原语。
最终标准：普通函数即可写 UI；可变事实有唯一所有者；多实例/分支/列表/弹层生命周期一致；
自定义外观不复制交互；测量重试不重复发布业务副作用；Agent 能追溯来源并拒绝过期目标。
原生 OS 验证与 headless 分开记录，未执行不得视为通过。
