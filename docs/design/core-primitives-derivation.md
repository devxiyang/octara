# 从核心原语推演分层架构

日期：2026-11-17。状态：**设计推演，未实施**。
接续[总方案](layered-architecture-redesign.md)与[交叉审查](../research/frontend-native-cross-review.md)。
本轮只核对当前导出与既有研究，未新增运行验证；下文能力分组不是新类型、新 crate 或已发布 API。
四个重点边界的具体默认政策、失败行为与公开面推导见[核心原语契约](core-primitive-contracts.md)。
后续讨论收敛：**不依赖 ui-kit 也必须能通过公开 core API 编写完整 UI**。
通用输入、编辑、语义、定位和交互能力不能由 kit 独占；kit 保留组合政策与默认外观。
下文“先留在 kit”的建议仅适用于组件专属装配/算法，不适用于通用能力。
依据和验证边界见 [W3C 原语审查](../research/w3c-core-primitives.md)。

## 1. 先确定什么算原语

推演顺序：事实及所有者 → 必要能力 → 组合规则 → 最小公开接口 → 组件反证 → 实现切片。
Field、Button、Combobox 是检验原语的用例，不是先定它们的外形，再让内核配合。
但“从下到上”也不意味着脱离真实组件提前设计通用系统：每项能力都必须说明解决什么实际组合问题。

区分三个层次：

| 层次 | 判断标准 | 例子 |
| --- | --- | --- |
| 应用公开原语 | 应用组合 UI 时可独立使用，有稳定且有限的语义 | 状态、派生、结构分支、keyed 列表、内容构造 |
| ui-kit 支撑能力 | 多种组件需要同一规则，但未必值得独立公开 | 控制根、标签关系、选项导航、弹层交互策略 |
| 内核私有机制 | 兑现前两层契约；应用不应手工驱动 | 执行准入、节点代次、挂载协调、布局失效、输出提交 |

内部机制可以复杂，但必须由具体契约解释。公开名称少并不意味着机制已经统一；
同样，内部有一个状态机不意味着必须增加一个公开原语。

### 1.1 熟悉的语义不是历史兼容义务

React、Base UI、Tailwind 等提供组合与使用体验的参考，不规定 Octara 的执行模型。
Agent 熟悉某种写法只是候选 API 的可学习性依据，不能压过所有权、原生交互与机制简单性。
每项借鉴都要回答：它解决的是普遍 UI 问题，还是特定宿主、语言或兼容要求产生的问题？
前者保留问题与契约，后者仅在 Octara 存在同样约束时采用。

| 值得保留的语义 | 不作为 Octara 默认前提 |
| --- | --- |
| 声明状态与 UI 的关系 | 重跑整个组件、按调用顺序识别状态、要求应用手工维护依赖数组或缓存来保证身份 |
| 内容与行为可组合 | 任意属性/事件/ref 合并，以及组件替换根节点后再补救角色和动作冲突 |
| 一致的布局、主题和状态样式 | 完整 CSS 兼容、任意 class 字符串解释、依靠选择器优先级修补组件边界 |
| 标签、描述、禁用和可访问动作 | 先实现鼠标交互，再由应用补齐键盘、AX 和 Agent 操作语义 |
| 弹层可改变展示位置 | 应用必须理解 DOM portal 的细节，或布局父链同时决定生命周期和全部交互归属 |
| 应用可控制业务值 | 每个属性都必须提供 controlled/uncontrolled 双套接口，或强制把编辑草稿与业务值视为同一事实 |
| 对异步结果和失效有明确处理 | 应用为每个组件手写取消、卸载存活检查和迟到结果过滤；框架负责其所有者和目标资格，业务仍负责请求相关性 |

以上是 Octara 的设计取舍，不是对所有前端框架现状的概括。
同样，不因选择原生就重造所有基础规则：文本组合输入、可访问性、键盘操作和平台约定是现实需求，
不能以“去历史包袱”为由删除。框架保证生命周期也不等于能自动判断任意业务请求的新旧。

新的默认方向是：普通 Rust 数据与显式能力、细粒度更新、作用域管理资源、类型化样式、
由同一语义行为接受不同输入路径。Root/Part、Model、Behavior 等现有或候选名称都可以重新审查；
不为了接近参考框架而保留抽象，也不为了显得不同而发明新术语。

### 1.2 从 Rune / Exact 提取可简化原语的机制

再次核对本地固定快照：Rune `3686e94a`、Exact `08c889a9`；未拉取远端或运行参考框架。
下表将源码事实与 Octara 的设计推论分开，不以框架较新作为机制更优的证据。

| 参考源码中的具体机制 | 对 Octara 的启发 | 采用边界 |
| --- | --- | --- |
| Rune Button 用 row 承载按钮根，label_with 替换视觉内容，显式 label 保持名称 | 以稳定语义根组合内容，普通 Rust builder 可以覆盖很多自定义需求 | 不照搬隐藏全部标签后代；嵌套交互和独立语义须有明确限制，不先建立通用 render/属性合并协议 |
| Rune El::modal 声明需求，由窗口运行时协调；Popover 另用 focus_return | 控件声明交互政策，窗口维护真实焦点和输入资格 | 不把所有弹层都当 modal，也不把每种政策都升级成公开原语 |
| Rune Measurement 限制可访问资源，Measured 才交给 apply | 用私有 Rust 类型与借用边界约束阶段能力，减少依赖调用者自律 | 不照搬全树重建和手工 memo version；测量仍可更新派生缓存，不能称其完全无副作用 |
| Exact 分别定义 can_hold_children、is_measured_leaf、is_replaced | 内容所有权、测量和布局参与分别建模，避免一个 leaf 标记包办全部含义 | Octara 可以选择更小的内容集合，不必复制 Exact 所有节点或公开对应 traits |
| Exact 的普通 slot 保留调用者词法作用域与 provider | 内容放置不暗中转移其逻辑所有者；组合边界应有可预测上下文 | 普通内容传递不必引入 Parts 注册；Exact 特定库出口的静态 slot 限制不推广到动态 UI |
| Exact 编辑协议保留同值回写下的 selection/composition，并仲裁预编辑期间的不同值回写 | 输入以编辑过程为基础，业务 value 同步不能破坏原生编辑 | Octara 仍须选择自己的重置/拒绝/提交政策，不直接复制事件名或各宿主数字过滤策略 |

源码入口与反例详见 [Rune 报告](../research/agent-rune-architecture-review.md)发现 1–5、
[Exact 报告](../research/agent-exact-architecture-review.md)第 2–4 节。
本次直接复核 Rune 的 actions.rs、el/focus.rs、runtime/commit.rs，
以及 Exact 的 kernel/src/node.rs 和 Apple FieldComposition.swift；其余依据沿用上述已读报告。

据此调整推演优先级：先确定内容能力、语义动作、编辑同步、逻辑所属四份小契约，
再判断哪些需要公开原语。优先用普通构造参数、builder、闭包和私有类型兑现，
只有这些手段不能自然表达真实组合时，才增加公开 Parts、trait 或新的状态对象。

## 2. 必须先成立的五条规则

1. **事实有唯一修改所有者。** 业务值归应用，编辑过程归编辑文档，焦点归窗口，资源归 App。
   接受值、编辑草稿和预编辑可以不同；必须定义同步规则，不能把它们当作任意可写的镜像。
2. **身份与关系有各自含义。** key 保持结构连续性，节点身份验证操作对象，名称用于查找；
   逻辑所属、布局父子、语义引用分别表达，不能靠同一个字符串或父链隐式推导。
3. **执行与释放分开。** 所有入口遵守已有执行政策，回调后重新检查资格；
   失去普通执行资格不阻断框架资源收尾。
4. **派生结果共享来源。** 样式、几何、语义投影可缓存，必须说明失效；
   绘制、命中、IME、AX 和 Inspector 不各自维护可独立修改的真相。
5. **组合不悄悄改变行为。** 换标签内容、布局或外观，不应丢失动作资格、编辑身份和逻辑所有者。

这些是跨层约束，不新增公开 Owner、Permit、Revision 或 Transaction 来承载它们。

## 3. 最小能力集合

下表是能力集合，不是“新增七个原语”。现有接口能满足的优先保留；缺口先明确契约，再决定类型。

| 能力组 | 应用需要表达什么 | ui-kit / 内核提供什么 | 本轮决定 |
| --- | --- | --- | --- |
| 状态与派生 | 可写状态、只读值、纯派生、来源明确的副作用 | 依赖图、观察边界、变更传播 | 保留 Signal / ReadSignal、state、memo、watch；不重造状态语言 |
| 所有权与工作 | 组件作用域、上下文、清理、随所有者结束的任务 | 执行准入、取消、释放、迟到结果校验 | 保留现有机制；不把内部 scope 管理全面公开 |
| 内容与结构 | 容器、文本、输入及媒体内容；条件、keyed 重复、组件边界 | 挂载、身份连续性、内部内容所有权、移除 | 重做内容能力契约；隐藏 View 挂载表示；共享结构协调 |
| 样式与几何 | 类型化布局、文本样式、条件样式；必要的几何/滚动操作 | 继承、token 解析、测量、编辑及展示几何 | 复用样式机制，补齐共享几何契约；不公开一套新布局引擎 |
| 语义与动作 | 角色、名称、描述、状态、可执行动作和应用通知 | 关系解析、统一动作资格、焦点/输入路由 | 明确复合根及真实控件的配置目标；复用 Behavior，审查其公开边界 |
| 编辑与选择 | 输入值及编辑/提交通知；列表的选项与选中值 | composition、selection、编辑历史；选项身份和导航 | 文本编辑与选项导航是不同领域；分别共享，不合成通用 Selection 系统 |
| 展示位置与交互边界 | 普通流、滚动内容、弹层；定位和模态等需求 | anchor、逻辑所属、焦点恢复、外部关闭、背景交互资格 | 提取最小共享政策；不先公开 Portal / Layer / FocusScope 全家桶 |

App / Window 是这些能力的运行宿主；初始化资源、窗口生命周期和输出协议另有明确入口，
不把它们塞进组件上下文大字典。Inspector 是读取事实和提交操作的工具，不增加 Agent 专用状态原语。

### 3.1 状态核心与专用工具分层

StateList / ReadList、TextBuffer 是有明确负载收益的增量工具，不要求普通列表或文本都使用。
AsyncMemo 属于异步工具；Model 属于值适配；untrack 只改变依赖收集。
这些对象不应为了减少名称而并入 Signal，也不应成为每个组件都必须经过的层。
是否移出常用 prelude 要等实际调用推演；不能用导出调整代替机制设计。

### 3.2 内容协议比 builder 名称先确定

先回答四个问题：谁拥有应用 children，谁拥有内部文本/链接，谁提供测量，谁产生语义后代。
“原子内容”表示不接受任意应用布局 children，不表示没有内部对象或语义后代。
不允许文本链接协调误删应用子节点；徽标和前后缀使用外部组合。
公开层用窄类型还是早诊断 builder，待比较普通组合成本后决定；低层结构入口仍须验证。

### 3.3 语义动作不是角色加鼠标回调

一个按钮根须协调角色、可访问名称、禁用、键盘激活、指针激活、AX/Agent 动作和焦点。
其中路由与动作资格归窗口/内核，按钮约定归 kit；不能要求应用逐项拼装后才获得正常按钮。
组件内部行为和应用通知保持既有顺序。通知不具备事后撤销作用；
若确需可取消意图，先明确它阻止哪一步，再决定接口，不能默认所有事件都可取消。

### 3.4 编辑协议独立于表单协议

核心编辑文档拥有 composition、selection、历史及文本几何；应用拥有业务接受值。
需要规定同值回写、不同值回写、组合提交/取消、业务拒绝以及目标替换后的迟到事件。
这是输入能力的必要契约，不用 Field 或 NumberField 各自绕过。
解析、范围、可选空值、提交时机和错误显示属于明确的上层政策。
因此不新增内核 Validator、FormStore 或全局 invalid 合并规则。

### 3.5 弹层先定义关系，再决定公开原语

同一弹层可能有不同的布局位置、逻辑所有者和焦点目标；迁移展示位置不能重建业务作用域。
定位、模态、外部关闭、焦点进入和恢复分别有政策。记录实际打开者并在恢复前验证存活。
先由 Dialog 与非模态输入建议验证共享机制；只有应用确实需要独立组合时才开放更低层接口。
部件注册依附既有生命周期，逐组件定义基数，在稳定边界检查完整性，不另建通用关系运行时。

## 4. 明确不归核心原语的对象

| 对象 | 归属及原因 |
| --- | --- |
| Button、Field、Dialog、Tabs、Combobox、Slider、NumberField | ui-kit 控件/组合契约；各自有产品层含义和不同交互政策 |
| Label / Control / Error / Trigger 等命名部件 | 按需提供的组件 API；不是所有组件统一实现的全局 Part 类型 |
| 选项导航、控制根、字段关系 | 先作为 kit 内共享实现；复用成立不自动意味着公开 |
| Model | kit 的读写适配；不能替代编辑文档或异步业务接受协议 |
| token / variant 中的组件外观约定 | kit / 品牌；底层通用颜色、文本、尺度及符号解析仍可保留 |
| 节点 ID、执行资格、失效版本、挂载槽位 | 内部正确性机制；仅工具和边界协议按需暴露不透明身份 |

## 5. 合并、删除与保留的方向

- **合并**：App 资源写入口、语义名称解析、结构移除及释放协调、共享选择导航、按钮变体的控制根。
- **删除**：公开挂载变体；任意内容都能接收任意 children 的承诺；内部链接与应用 children 混用；
  复合组件返回裸 El 即可代表所有部件的承诺；已有 keyed 路径足够时的选项镜像。
- **保留但收窄**：Behavior、样式/条件机制、专用增量工具、执行政策、编辑与焦点机制。
  保留机制不等于保留所有当前签名；删除前要证明所有调用已迁移。
- **暂不新增**：统一 Widget trait、公开通用关系引擎、完整 headless crate、全局表单系统、第二个响应式运行时。

## 6. 用三个案例反证原语是否足够

先画清每个案例的状态与所有者、结构/语义关系和事件顺序，再推演 Rust 调用形状。
不在这一阶段编造看似已可用的 API，也不改实现。

| 案例 | 必须由现有或候选基础能力自然表达 | 暴露的失败意味着什么 |
| --- | --- | --- |
| 图标 + 动态文字 Button | 一个动作根、稳定焦点、正确名称、禁用、可替换布局与外观 | 需要覆盖角色或重新接线，说明内容/语义行为边界有缺口 |
| 有前后缀和错误说明的输入 Field | 实际输入获得 label/description；组合更新不丢 IME；空值政策明确 | 只能给包装节点加属性或强制重挂载，说明配置目标/编辑协议有缺口 |
| 弹层内输入建议 | 逻辑所属保持；编辑焦点与 active 选项不同；结果重排稳定；非模态关闭/恢复有定义 | 依赖字符串拼接、另建焦点/编辑状态，说明关系/身份/窗口政策有缺口 |

同一能力至少要能说明另一种合理用法，才考虑抽出通用公开 API。
此处不是机械的“两处使用才抽象”：正确性所必需的内部边界可以先建立，公开承诺需要更强证据。

## 7. 本轮推演的完成标准

每个拟公开能力必须写清：调用者、所有者、输入与输出、合法执行阶段、身份连续性、移除/失败后的结果。
每个拟新增抽象必须指出替代的旧路径；每个删除项必须列出仍需保留的用途。
三个案例在纸面上能表达完整行为，且不要求应用访问 Kernel 私有状态或复制编辑/焦点机制。
再确定公开签名与模块边界，进入总方案 A–E 的实现切片。
