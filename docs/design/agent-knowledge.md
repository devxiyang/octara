# Giving Agents the Full Usage of the Framework

Based on [research](../research/agent-knowledge.md). Confirmed: the registry is generated from rustdoc JSON; CLI first, MCP later wraps the same
commands; finish animation first, then do this.

## One source, many outputs

```
Code (public API and rustdoc)
  └─ generate: api.json (own stable format, versioned, committed to the repo; a test checks it is not stale)
       + data in the kernel: built-in commands, keymap, diagnostic codes, tokens, spring presets, roles
            └─ catalog: one entry per usage (name, kind, signature, one-line summary, example id, related entries)
                 ├─ skill octara (SKILL.md + references/: index, start-here), octara skill install puts it into the app project
                 │    └─ a standing-guidance section in the project AGENTS.md (between markers), pointing to the skill and lookup commands
                 ├─ octara vocab <name> / octara explain <code> (CLI, JSON output)
                 ├─ MCP (later, wraps the CLI)
                 └─ llms.txt / llms-full.txt (secondary)
```

- Generation uses nightly rustdoc JSON (`cargo +nightly rustdoc -- --output-format json`), needed only at generation time; it is converted to our
  own format, pinning `format_version`.
- Only concepts and "when to use which" are handwritten; signatures and docs are always generated.

## Distribution (confirmed: skill + standing guidance)

- This repository's `AGENTS.md` is only for people and Agents developing Octara: safety rules and this repository's working rules.
- Knowledge for writing apps with Octara is the skill `octara`, generated by the CLI and matching the version: `SKILL.md` (core rules, common
  pitfalls, how to look things up), `references/index.md` (compressed index), `references/start-here.md`.
- `octara skill install`: the primary copy is written to the project's `.agents/skills/octara/` (most Agents read here); when Claude Code or Kiro is
  detected, symlinks are created in `.claude/skills` and `.kiro/skills` (copy if that fails); `--global` installs to `~/.agents/skills` (the user
  directories of Claude Code and Amp use links); `--agent` selects; `--check` checks whether it is stale, and running it again updates.
- On install, a standing-guidance section is written to the project `AGENTS.md` (between markers, safe to repeat): this project uses Octara, read the
  skill before writing UI, look things up with `octara vocab` / `octara explain`; if the project has a `CLAUDE.md`, add `@AGENTS.md` to it. Based on
  Vercel's evaluation: a skill alone is often not invoked.
- The repo keeps a generated copy in `skills/octara/` (a test checks it is not stale), installable with `npx skills add octoii-works/octara`.

## Reading order

1. The standing guidance in the project `AGENTS.md` → the skill `SKILL.md`: core rules, common pitfalls, where to look; `references/index.md` lists all names.
2. `docs/start-here.md`: the only required page (about 300 lines).
3. The other docs state at the top "for lookup, do not read through"; look up by name with `octara vocab`.
4. `recipes/`: one topic per article, with a byte limit, snippets compiled and run in CI; `examples/` are complete apps that can be grepped.

## The running framework answers questions

- `octara check`: build + headless checks (layout issues, accessibility tree, diagnostics, light and dark themes, phone and desktop sizes), JSON
  output; "clean means done".
- `octara inspect` / `octara run --script`: the semantic tree (test id, role, state, source location, available commands), act by test id, advance
  the clock, `pending`, screenshots; this is the ROADMAP P3 Inspector protocol, versioned.
- Diagnostics: a stable code + cause, symptom, fix, doc anchor; the same text serves compile time (`#[diagnostic::on_unimplemented]`,
  `#[must_use]`), runtime, the CLI and tests (`compile_fail` pins the error text).

## Inspector protocol and checks

Based on Exact's `verify` and agent stdio, Rune's `--tree` / `--script`, and GPUI's test driver.


- **Entry point**: the app declares `[package.metadata.octara] view = "my_app::app"` (`fn() -> View`) in `Cargo.toml`. The CLI generates a standalone
  inspection program in `target/octara/harness/`: it depends on the app (by path), copies the app's way of writing the `octara` dependency (same
  source and version), copies the app's `Cargo.lock`, and shares the app's `target/`. The inspection program only calls `octara::inspect::serve(view)`.
- **Judgment lives in the core**: snapshots, script execution and checks are all in `octara::inspect`, matching the `octara` version the app actually
  uses; the CLI only builds, launches and formats; the protocol is versioned, and a mismatch is reported.
- **Snapshot** (`octara.inspect/1`): viewport, theme, breakpoint, time, focus, pending work count, and nested nodes: `id` (test id, or the path if
  there is none), `role`, `name`, `text`, `value`, `checked`, `expanded`, `states`, `bounds` (presented geometry, rounded to 0.1), `actions`,
  `commands`, `source`, `children`. Absent fields are not output; within one major version, fields are only added, never changed.
- **Script**: JSON lines, the same protocol as the interactive one on stdin/stdout: each line is an `op` (`tap`, `press`, `type`, `key`, `advance`,
  `settle`, `size`, `theme`, `inspect`, `expect`), each line gets a reply `{"ok":true,..}` or `{"ok":false,"code":..,"message":..}`; `expect` asserts
  text, existence, state, value, no issues. It stops on failure, with a non-zero exit code.
- **`octara check`**: light and dark themes × phone (390 × 844) and desktop (1280 × 800); each cell checks layout issues, diagnostics, pending work
  left after settling, accessibility (actionable elements without a name, tap targets smaller than 44 × 44 on phone, text contrast below 4.5:1 /
  large text 3:1). New checks are all registered diagnostic codes. The same issue across cells is merged and the cells it appears in are listed.
  Warning and above are not clean, Info does not count; the app can `accept` in metadata (code, node, required reason).
  Exit codes: 0 clean, 1 issues, 2 build or launch failure. Text by default; `--json` outputs `octara.check/1`.

## Staying correct

- Examples are tests; recipe byte limit; `--help` and argument parsing are aligned by tests; if `api.json` is stale, the test fails.
- Pitfall list: reproducible, dated, written as "symptom → cause → what to do"; deleted once superseded by a diagnostic.
- `octara feedback note`; evaluation on a fixed task set (with and without each material), failures counted by diagnostic code.

## Implemented

- Diagnostic code registry: `octara::diagnostics::CODES`, each code fixing severity, category, one-line summary, cause, fix and doc anchor;
  `Runtime::diag` and the layout checks accept only a registered `&Code`; tests check that anchors exist, that codes mentioned in source and docs are
  all registered, and that every registered code has a place that reports it.
- Usage registry and `octara vocab` / `octara explain`: on each run, merged in memory from `api.json` and the kernel data (`diagnostics::CODES`,
  `BUILTIN_COMMANDS` and `Keymap::standard`, `Token::BUILTIN` and themes, `Spring::NAMED`), not stored in a file; text output by default (saves
  tokens), `--json` outputs structured data.
- Inspector protocol and checks in the core: `octara::inspect` (`Snapshot`, `Request` / `Reply`, `run_script`, `check`);
  `octara check` / `inspect` / `run [--script]` build a harness around the app named in `[package.metadata.octara]`.
- The index is generated by `octara index` (size has a limit, not a target); the code blocks in `docs/start-here.md` are doctests of `octara-cli`.
- `api.json`: `crates/octara-cli/api.json`, generated by `octara api`, checked by `octara api --check` and a test; without nightly it reports an error
  and gives the install command.
