# Giving Agents the Full Usage of the Framework

Based on [research](../research/agent-knowledge.md). Status: confirmed; implemented, evaluation
not yet.

## What is worth providing

Models grow stronger at knowing and reasoning; they do not grow able to see what only the
running app knows. So Octara provides:

- **The semantics a model cannot infer from the source quickly**: one short page
  (`start-here.md`) on what differs from the web and from other frameworks (a component runs
  once, reads go in closures, boxes do not shrink by default).
- **Lookups over what is generated**, not hand-written catalogs: signatures and docs come from
  rustdoc; kernel data (commands and their keys, theme tokens, springs, diagnostic codes) comes
  from the kernel.
- **Facts from the running app**: the semantic tree, pictures and what they can be trusted for,
  layout issues, diagnostics, pending work, deterministic replay.
- **What a person points at**: component boundaries and picking.

It does not provide what compensates for a weak or short-context model: compressed indexes and
byte budgets, recipes, per-diagnostic fix texts, numbered marks over pictures, size
explanations. What stays is decided by evaluation: a fixed task set run with and without each
piece (see Order).

## One source, several outputs

```
The source of the octara crates the project depends on (`cargo metadata` finds them)
  └─ read with syn (stable Rust): modules, `pub use` (globs too), items, impls, doc comments,
     lines; the framework's own macros expanded (`steps!`), and bitflags! / new_key_type!
     cached in <target>/octara/api.json until a source file changes
       + data in the kernel: built-in commands, keymap, diagnostic codes, tokens, spring presets
            └─ catalog: one entry per name (kind, signature, summary, related entries, facts)
                 ├─ skill octara: SKILL.md, references/start-here.md, references/api/ (an index
                 │    of crates and modules, a file per module, one line per item with its
                 │    signature, summary and file:line); `octara skill install`
                 │    └─ a standing-guidance section in the project AGENTS.md (between markers)
                 └─ octara vocab <name> / octara explain <code> (text, or JSON)
```

- Nothing generated is checked in, and no nightly toolchain is needed: the API always matches
  the version the app builds with.
- What a reader of the source cannot see as rustdoc would: generic bounds of blanket impls'
  targets are as written, macros other than the framework's own and the two named are left
  unexpanded. Every line says where it is defined, so the source settles what the line does not.
- Only concepts and "when to use which" are handwritten; signatures and docs are read.

## Distribution

- This repository's `AGENTS.md` is for developing Octara: safety rules and working rules.
- Knowledge for writing apps is the skill `octara`, generated by the CLI for its version:
  `SKILL.md` (rules, how to look things up), `references/start-here.md`, and
  `references/api/` (written at install, for the version the project uses).
- `octara skill install`: the primary copy in the project's `.agents/skills/octara/`; symlinks
  where Claude Code or Kiro is detected (a copy if that fails); `--global`, `--agent`, `--check`.
- Install writes a standing-guidance section to the project `AGENTS.md` (between markers): the
  project uses Octara, read the skill before writing UI, look names up with `octara vocab`; a
  `CLAUDE.md` gets `@AGENTS.md`.
- The repo keeps a copy in `skills/octara/` without `references/api/` (a test checks it is not
  stale), installable with `npx skills add octoii-works/octara`; its `SKILL.md` says to run
  `octara skill install` for the reference.

## The running framework answers questions

- `octara check`: build and headless checks (layout issues, accessibility, diagnostics, light and
  dark themes, phone and desktop sizes); "clean means done".
- `octara inspect` / `octara run --script`: the semantic tree (test id, role, state, source,
  component boundaries, commands), acting by test id, the clock, `pending`, captures, `pick`.
- Diagnostics: a stable code, its cause (with the rule behind it where the rule is Octara's own)
  and a doc anchor; `octara explain <CODE>` reads them, and finds a code inside a pasted message.

## Inspector protocol and checks

Based on Exact's `verify` and agent stdio, Rune's `--tree` / `--script`, and GPUI's test driver.

- **Entry point**: the app declares `[package.metadata.octara] view = "my_app::app"`
  (`fn() -> View`) in `Cargo.toml`. The CLI generates a harness in `<target>/octara/harness/`: it
  depends on the app by path, writes the `octara` dependency as the app does, starts from the
  app's `Cargo.lock`, and builds into the app's target directory.
- **Judgment lives in the core**: snapshots, scripts and checks are in `octara::inspect`, so
  they match the `octara` the app uses; the CLI builds, launches and formats.
- **Snapshot** (`octara.inspect/1`): viewport, theme, breakpoint, time, focus, pending work,
  windows, and nested nodes: `id`, `role`, `name`, `value`, `checked`, `expanded`, `states`,
  `bounds` (presented, to 0.1), `actions`, `commands`, `native`, `icon`, `source`, `component`
  (where one starts), `children`. Absent fields are left out; within a schema version fields
  are only added.
- **Script**: JSON lines, the same protocol as the interactive one: each line is an `op`, each
  gets `{"ok":true,..}` or `{"ok":false,"code":..,"message":..}`; it stops at the first failure.
- **`octara check`**: light and dark × phone (390 × 844) and desktop (1280 × 800); each cell
  checks layout issues, diagnostics, work left after settling, and accessibility (unnamed
  controls, small targets, contrast). The same finding across cells is merged; Warning and above
  are not clean; the app can `accept` a finding with a reason. Exit codes: 0 clean, 1 findings,
  2 build or launch failure.

## Staying correct

- Examples are tests; `--help` and argument parsing are aligned by tests; a stale skill copy
  fails a test; the API reader is tested against the framework's own source (canonical paths,
  macro-written methods, impl bounds, re-exports, lines).
- The diagnostic registry: `octara::diagnostics::CODES` (severity, area, summary, cause, doc
  anchor); reports take only a registered `&Code`; tests check that anchors exist, that codes
  named in source and docs are registered, and that every registered code is reported somewhere.

## Order

1. Evaluation: a small fixed task set (build a list with a field, fix an overflow, change what a
   person picked), run with the current model with and without each piece of guidance (the
   API reference, `vocab`, the skill, `start-here`), measuring success, tokens and fix rounds. Whatever
   does not change the result goes; rerun with each model generation.
