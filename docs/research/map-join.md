# Incremental `map` and `join` for keyed ordered collections

Scope: prior art and recommended semantics for Octara's next two stage operators, `map` (per-item transform) and `join` (item plus data from another collection).

Sources: Octara repo (paths relative to the repo root); reference clones (paths relative to `~/code/archive/reference/`); general knowledge marked "known" (not re-verified in this pass, no web access used).

## map

- **DBSP / Differential Dataflow** (known): `map` is linear, so its incremental version is itself: apply `f` to each record in the change (delta); DD `map` is stateless, no arrangement. A changed value is a retraction of `f(old)` plus an insertion of `f(new)`; weights make this uniform. Cost O(|delta|) calls of `f`, zero memory. Nothing memoized: a retraction recomputes `f(old)` (in Octara we can store the output instead).
- **SolidJS `mapArray` / `<For>`** (known): keyed by item reference identity (not a key fn); `mapFn(item, indexSignal)` runs once per item inside its own `createRoot`, disposed when the item leaves the array; the index is a signal. Whole mapping re-runs when the source array signal changes: an O(n) diff (with prefix/suffix fast paths) every time, even for a one-item change. A signal read inside `mapFn` is tracked by that row's root (not the diff), so the row's output does not recompute: reactive reads in `mapFn` build fine-grained effects, not a recompute of the row.
- **SolidJS `indexArray` / `<Index>`** (known): keyed by position; the item is a signal, `mapFn` runs once per index; replacing the value at an index updates that signal instead of re-running `mapFn`. This is the closest shape to Octara's "per-key item signal", but it is index-keyed.
- **Leptos `For`** (known): `key` fn plus `children(item)`, children run once per key under their own `Owner`, disposed on removal; keyed diff is O(n) over the whole vector on change. Item data is a plain value unless the app stores signals inside (idiom: `RwSignal` per row). `Store` keyed fields give per-key access in newer versions (unverified).
- **Svelte keyed each** (known): `{#each items as item (item.id)}`; Svelte 5 makes `item` a per-block source updated in place when the keyed array changes, so block bodies re-run only for what reads `item`. Diff is O(n) over the array. Rows have their own effect scope, torn down on removal.
- **Rune** (`rune/research/06-reactivity-animation.md:80-83, 166-170`): rejects signals; notes a keyed `<For>` "diffs the whole source on each change (O(n))" and a signal per row costs "around 100 B or more each (est.)"; keys are explicit and required on dynamic children, duplicate key fails loudly. `PLAN.md:223`: huge lists use a sum tree and views only for realized rows. No `map` operator: views are plain functions rebuilt from models.
- **Exact** (`exact/runner/src/runner/collection.rs`, `exact/docs/`): collection code is viewport/geometry feedback for hosts; nothing on mapping or joining collections (none).
- **GPUI / Zed** (`zed/crates/gpui/src/elements/uniform_list.rs:22`, `list.rs:490`): `uniform_list(id, item_count, |range, ..| Vec<R>)` is a pull-model renderer given a visible range; `ListState::splice(old_range, count)` tells a `SumTree` of heights that a range was replaced. Items are not keyed or mapped; "map" is the render closure itself, called for the visible range only (the analogue of Octara's `virtual_each`). No join.

## join

- **DBSP** (known; `docs/research/papers/incremental-collections.md` cites the paper): join is bilinear, so `delta(A join B) = dA join B + A join dB + dA join dB`, i.e. with integrated state `I(A)`, `I(B)`: `dA join I(B)` + `I(A) join dB` (the cross term folds in). Needs both inputs kept as indexed integrals (hash index on the join key). Cost per delta record: O(1) index probe plus O(matches). Memory O(|A| + |B|).
- **Differential Dataflow `join`** (known): both inputs arranged (`arrange_by_key`): an LSM-like trace of sorted batches, merged in the background; a new batch on one side probes the other side's trace. Arrangements are shareable between joins. Output is a collection of `(key, (v1, v2))` with product multiplicities: a duplicate on either side multiplies output rows.
- **Materialize** (known): SQL on DD; maintains arrangements per join input and shares them between views; delta joins (multi-way) avoid intermediate arrangements at the cost of one index per input per join order. Known failure: memory = arrangements; a hot key (many matches) makes one retraction fan out to every match.
- **Lookup join vs general join**: if the right side is keyed by the join key (functional dependency), each left row has at most one match, so output rows = left rows: key = left key, order = left order, and a left event is O(1) probe. Only a right event fans out, bounded by the number of left rows pointing at that right key (needs a reverse index `right key -> left keys`). A many-to-many join has output rows = matches, so its key must be the pair `(left key, right key)`, order needs a rule (left-major, then right order), and a left insert costs O(matches).
- **Missing right key**: a lookup join is a left outer join by default (`Option<R>`, `None` until the right row arrives, then an update, not an insert, because the left row's identity is unchanged). Inner join = `.join(..).filter(|j| j.right.is_some())`. DD/SQL inner joins drop the row, which in a UI makes rows vanish and remount (state lost) when a user is deleted; keep rows.
- **Key collisions**: right is a keyed stage, so its keys are unique (`DUPLICATE_KEY` at the source); multiplicities (DD) never arise. Output keys equal left keys, so no new collisions. Many-to-many pair keys `(LK, RK)` are unique iff both sides are.
- **Solid stores / derived** (known): a row does `users[msg.user_id].name`; fine-grained store proxies track that one property, so renaming a user re-runs only bindings that read it. This is a per-row lookup join with free fan-out, but you cannot filter or sort by the joined field without recomputing the pipeline.
- **Redux / reselect** (known): selectors memoize on input identity; a per-row selector factory (`makeSelector()` per component) is the recommended pattern; any change to the `users` map recomputes every row-selector's input check, O(rows). No incremental join operator.
- **Apollo normalized cache** (known): entities stored by `__typename:id`; relations are references; a field read watches the entity fields it touched, so renaming a user re-broadcasts only to queries that read that field. No join operator: join is a reference chase at read time.
- **SwiftData `@Query` / `@Relationship`** (known): the relationship is a stored pointer, not a join; the `@Query` re-fetches on store changes and Observation tracks per-property reads. Sort/filter by related fields is done in the store's predicate (SQL join), re-run, not incremental.
- **Room `@Relation`** (known): runs the parent query, then a second `IN (ids)` query per relation and stitches in memory; the invalidation tracker re-runs queries when any table touched changes (table-level, not row-level): any `users` write re-queries all joined results. Jetpack Paging 3 (known): `PagingData.map` transforms items page by page, lazily, `insertSeparators` adds rows; no join; refresh re-queries via `PagingSource` invalidation.
- None of these gives an incremental join with sort/filter on the joined fields; DD/Materialize/DBSP do, at index-memory cost.

## Cost and failure modes

| Operation | Per event | Extra memory |
| --- | --- | --- |
| `map`, any upstream event | O(1) hash + one call of `f` (update/insert); remove O(1); order is the upstream's, no treap needed | one output `Signal<U>` + map entry per key |
| lookup `join`, left insert/update/remove | O(1) probe (+ O(1) reverse-index edit) | per left row: output signal, cached right key, reverse-index entry |
| lookup `join`, right update | O(m) updates, m = left rows pointing at that key (`set_internal` + emit update each) | none beyond the above |
| lookup `join`, right insert/remove | O(m) rows flip `None <-> Some` (m = rows waiting on that key, so the reverse index also holds absent keys) | reverse index sized by distinct left join keys |
| many-to-many `join` | left insert O(matches), right update O(matches) | pair seq O(|pairs|) |
| downstream `sort_by` after a join | each fan-out update is one O(log n) rank check | none |

- Fan-out explosion: a popular right row (user with 100k messages, a "default" tag) makes one write cost O(m) and flood downstream sort/filter and the UI log. Solid/Apollo avoid this only because lookups are lazy per mounted row; with `virtual_each` mounted rows are ~80, so a lazy variant is an option, but it forfeits sort/filter on joined fields.
- Mitigations: skip the update when `R` compares equal (`PartialEq`); expose a projection `join(&right, key, |r| r.name.clone())` so only the used field is compared, and unchanged projections do not fan out (a rename touching `avatar` changes nothing).
- Transient states: events are synchronous, not transactional; a left row may arrive before its right row (`None`, then `Some`). Accepted, consistent with `Checked` (`reactive-core.md` section 7), which will verify the final state.

## Conclusions

1. `map`: `source.map(|t: &T| -> U) -> Derived<K, U>` (`U: Clone + PartialEq + 'static`). Same keys, same order. `f` is pure and runs untracked (like `filter`'s `pred`), not a reactive scope; there is no per-row owner (the row's scope is `each`'s, which already keeps state across Moves).
2. `map` owns one `Signal<U>` per key (`Signal::detached`, disposed on remove, as `FlatInner::take`). Eager and observer-driven: insert/update call `f` once; an update emits `updated` only if `new != old`. Order and `index_of` delegate to upstream (no `Seq`), so it adds O(1) per event and no ordering memory; Move events pass through.
3. Then `flatten` becomes a concatenation of `map`ped members and the doubled entry memory of section 9 goes away (design follow-up; needs a confirmed decision before changing `flatten`).
4. `join` v1 is the lookup join: `left.join(&right, |l: &L| -> RK) -> Derived<LK, Joined<L, R>>` with `Joined { left: L, right: Option<R> }`, where `RK` is the right stage's key type (so unique by construction). Output key = left key; output order = left order (delegated, as in `map`); left outer by default, inner via `.filter`. A missing right key is `None` and later an `updated`, never an insert/remove.
5. Propagation: left insert/update probes right (O(1)) and refreshes the reverse index if the join key changed; right update/insert/remove looks up the reverse index and updates all m dependent rows (O(m)); left removal drops its reverse-index entry. The projection form `join(&right, key, |l, r: Option<&R>| -> U)` should be the only form, so only the used fields are compared (`PartialEq`); a `Joined { left, right }` row is that projection with both sides cloned.
6. Many-to-many is not v1. Express it today as a link `list` keyed by `(todo_id, tag_id)` and `join` it to each side; if a native operator is needed later: output key `(LK, RK)`, order left-major, with `FlatKey`-style `Display`.
7. Per-event cost to document: map O(1) + `f`; lookup join O(1) left, O(m) right (m = rows referencing that key); memory O(|left|) for reverse index and output signals. Run both through `Checked` (rebuild-from-scratch comparison).
8. Diagnostics to register in `octara::diagnostics` (proposed, severity/anchors to be chosen): `JOIN_FANOUT` (warning: one right change updated more than a threshold of rows, e.g. 10,000 (a guess); cause: a hot right key; fix: join a narrower projection, or paginate/virtualize before joining); `JOIN_MISSING_KEY` (warning, reported once per call site by the existing code+location dedupe, only for the strict variant that treats `None` as an error); `MAP_READS_STATE` (warning: `f`/key fn read a tracked signal, which would go stale; reuse the `STRICT_READ_UNTRACKED` detection, fix: put the signal inside the item, or `join`). `DUPLICATE_KEY` already covers key collisions.
9. Open question for confirmation (changes agreed semantics only if the answer differs): the "left join keeps rows" default (versus SQL inner-join dropping rows), and whether `map`/`join` closures are untracked, matching `filter`/`sort_by`.
