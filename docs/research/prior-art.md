# Research: Community experience with mainstream cross-platform and declarative UI frameworks

Status: research notes (2026-11). Compiles the problems, community criticism and official corrections that surfaced over the years
of evolution of React, React Native, Expo, Flutter, SwiftUI, Jetpack Compose and the Web Signals frameworks, and distills lessons
for Octara. Items marked "secondhand" come from third-party articles and need to be checked against the official release notes
before being cited.

## 1. React

**Model:** component functions re-execute when state changes, producing a virtual tree that is diffed.

**Community criticism and official corrections:**

- **Rules of Hooks:** state identity is determined by call order, and calling a hook conditionally misaligns state; lint rules are
  needed as a backstop.
- **Stale closures:** an omitted `useEffect` / `useCallback` dependency array entry silently reads an old value. This shows that
  **rebuild models have the silent-stale-value problem too**, not only Signals.
- **Burden of manual memoization:** `useMemo`, `useCallback` and `React.memo` proliferate; omissions cause performance regressions
  and excess use raises complexity. The official final solution is [React Compiler 1.0](https://react.dev/blog/2025/10/07/react-compiler-1)
  (2025-10): automatic fine-grained memoization at build time.
- **Effect abuse:** the official documentation has a dedicated "You Might Not Need an Effect", to correct the practice of using
  Effects as a data synchronization tool.

**Lessons:**

- The performance of a rebuild model ultimately depends on the compiler for automatic memoization. Rust has no such compiler
  plugin and can only rely on proc-macro rewriting, which agrees with the conclusion of Rune `research/38`.
- User-defined Effects are a high-frequency misuse point, and the framework should route updates through declarative bindings as
  much as possible.
- Using call order or source location as state identity is fragile; explicit keys should be used.

## 2. React Native

**Problems of the old architecture:** JS and native communicated through an asynchronous, batched, JSON-serialized Bridge, which
caused:

- no synchronous layout measurement or synchronous calls to native methods;
- dropped frames in gestures, animations and long lists when the JS thread is busy;
- all native modules initialized at startup, making startup slow.

**Official correction:** the New Architecture provides synchronous calls through JSI, synchronous layout and concurrent rendering
through Fabric, lazy loading through TurboModules, and typed interfaces generated by Codegen. The New Architecture became the
default in 0.76, and from [0.82](https://reactnative.dev/blog/2025/10/08/react-native-0.82) (2025-10) only the new architecture
is supported and the old one can no longer be enabled. The whole migration took years, and adapting ecosystem libraries was the
main obstacle.

**Corrections made spontaneously by the community:**

- **Animation and gestures:** Reanimated's worklets run on the UI thread and Gesture Handler recognizes gestures on the native
  side, moving animation and gestures off the JS thread. This is the same conclusion as Rune's "the render thread owns animation".
- **Long lists:** FlatList's performance problems gave rise to Shopify's FlashList (view recycling).

**Lessons:**

- Once the shape of the native boundary is fixed, changing it costs years. The interfaces of Native Modules and Native Islands
  should support synchronous calls, be typed and be tool-generated from the start; async is for real I/O only.
- Animation, gestures and scrolling cannot depend on the application logic thread.
- List virtualization and view recycling must be built-in framework capabilities, not left to the ecosystem to fill in.
- Using each platform's native controls directly lets platform differences leak into application code, and cross-platform
  consistency is hard to guarantee.

## 3. Expo

Expo mainly addresses toolchain and native extension problems, not rendering.

**Widely acknowledged practices:**

- **Expo Modules API:** writing native modules in a declarative Swift / Kotlin DSL, which significantly lowers the barrier to
  native extension.
- **Config Plugins + Continuous Native Generation:** native projects are generated from configuration (`prebuild`) and not
  committed to the repository; native capabilities are composed as "package + config plugin".
- **Development Build:** a custom development client that needs rebuilding only when native dependencies change, with JS changes
  taking effect immediately.
- **Expo Router:** a file-based routing convention that lowers the design cost of navigation.

**Criticism:** the cloud build and release service (EAS) brings a service dependency; major SDK upgrades still require
considerable migration work.

In 2026-11 the Expo team open-sourced Exact, a new Agent Native framework that is not based on React Native, recorded separately
in [Exact research](exact.md).

**Lessons:** corresponding to Octara's Native SDK and Development Toolchain layers —

- Native projects should be generated by tools, and native capabilities composed as crates plus declarative configuration, rather
  than developers maintaining Xcode / Gradle projects by hand;
- Native modules should be written in a typed, declarative way and able to generate cross-language bindings;
- Development builds and fast iteration of application logic should be separated.

## 4. Flutter

Flutter is architecturally closest to Octara: self-drawn UI, retained tree, a consistent cross-platform look, plus native view
embedding.

**Three trees:** Widgets are immutable and rebuilt each time; Elements preserve identity and hold State; RenderObjects handle
layout and painting. `const` widgets can skip rebuilds. Stateful hot reload works because State hangs off the Element tree and is
not lost when code is rebuilt.

**Community criticism and official corrections:**

- **Fragmented state management:** the official offering is only `setState` and `InheritedWidget`, and the ecosystem has Provider,
  Riverpod, Bloc, GetX, MobX and others side by side, with no unified answer for a long time.
- **Shader compilation jank:** Skia compiled shaders at runtime, dropping frames the first time an effect appeared. The official
  fix is Impeller, which precompiles shaders: iOS uses Impeller by default; Android uses Impeller by default on API 29+
  (secondhand: since 3.27).
- **Platform Views:** embedding native views still requires trade-offs among several modes, see the
  [official documentation](https://docs.flutter.dev/platform-integration/android/platform-views):
  - texture layer mode can stutter during fast scrolling;
  - hybrid composition merges the raster thread with the platform thread, lowering Flutter's frame rate;
  - the new HCPP mode gets both, but is still experimental and requires Android API 34+, Vulkan and Impeller.
- **Text input and native feel:** text editing, selection, the magnifier and autocorrect on iOS have long been criticized as
  "uncanny valley". Rune's research mentions that Flutter's iOS text adaptation layer is about 3,400 lines and still not natural
  enough.
- **Metaprogramming:** after the Dart team prototyped macros for years, they were
  [cancelled in January 2025](https://dart.dev/blog/an-update-on-dart-macros-data-serialization), and code generation continues to
  rely on build_runner.
- **Accessibility:** Flutter maintains a Semantics tree independent of rendering and maps it onto each platform's accessibility
  interface. This is a direct precedent for Octara's "semantic tree shares its definition with AccessKit".

**Lessons:**

- The framework must provide a first-class state solution. Fragmentation hurts agents more: training data and examples
  contradict each other.
- The rendering pipeline and shaders should be built in advance and not compiled for the first time at runtime.
- Native Islands are a long-standing hard problem: after years of investment, Flutter still has no solution that balances
  fidelity and performance in all scenarios. Octara must explicitly report each platform's capability boundaries
  (`ARCHITECTURE.md` already has this principle, and Flutter's experience proves it cannot be omitted).
- Text input should directly implement each platform's native protocol, and the most engineering investment should be reserved
  for it.
- Do not bet the core development experience on language metaprogramming that has not landed.
- Retained identity plus externally held state is the prerequisite for stateful hot reload.

## 5. SwiftUI and Jetpack Compose

These two bear directly on the state-model debate: both are rebuild models, and both are evolving toward finer dependency
granularity and automatic skipping.

**SwiftUI:**

- `ObservableObject` invalidates at object granularity: a change to any `@Published` field makes all observers recompute. iOS 17
  introduced `@Observable`, which tracks by the fields actually read.
- Identity problems: the semantics of structural identity, `AnyView` and `.id()` are easy to get wrong, causing state to reset
  unexpectedly or animations to misbehave.
- The type checking of the result builder DSL can time out, and the errors are hard to locate. This is further evidence against a
  DSL as the View API.

**Jetpack Compose:**

- Stability inference decides whether a composable can be skipped; a slight change in parameter types loses the ability to skip,
  and is hard to diagnose. The official fix is
  [strong skipping](https://developer.android.com/develop/ui/compose/performance/stability/strongskipping): on by default since
  Kotlin 2.0.20, composables with unstable parameters can also be skipped, and lambdas are automatically memoized.
- The official recommendation is to defer state reads with lambda-form modifiers so that animation enters only the draw phase,
  skipping composition and layout. Reading the same value in the composition phase causes recomposition on every frame, without
  any warning.

**Lessons:** the rebuild model is evolving toward field-level tracking, compiler-driven automatic skipping, and high-frequency
values bypassing rebuilds. In Swift and Kotlin these mechanisms are all provided by the compiler; in Rust they can only be
implemented with the runtime or proc macros.

## 6. Web frameworks turn to Signals

Over the past few years, most mainstream Web frameworks have introduced or turned to Signals-style fine-grained reactivity:

- SolidJS has Signals at its core; Preact provides Signals;
- Angular introduced Signals and is advancing zoneless change detection;
- Svelte 5 replaced compile-time-inferred reactivity with runes (based on Signals);
- Vue's Vapor Mode compiles to direct DOM operations without a virtual DOM, and as of October 2026 is still at the 3.6 RC stage;
- TC39 has a Signals standardization proposal.

React is the main exception: it keeps the re-render model and chooses to solve performance with a compiler.

## 7. Summary of lessons for Octara

| Area | Lesson | Source |
| --- | --- | --- |
| State model | Both kinds of model are converging on "fine-grained dependency tracking + retained identity"; the difference is the unit of update and who does the memoization | React Compiler, SwiftUI, Compose, Web Signals |
| State model | Silent stale values are not unique to Signals; React's dependency arrays produce them too | React |
| State model | The framework must provide a first-class state solution to avoid ecosystem fragmentation | Flutter |
| State identity | Explicit keys beat call order or source location | React Hooks, SwiftUI, Rune |
| Animation / gestures | Must be decoupled from the application logic thread | Reanimated, Compose deferred reads, Rune |
| Lists | Virtualization and view recycling must be built into the framework | FlashList, Rune |
| Native boundary | Synchronous, typed, code-generated; once the interface shape is fixed, changing it takes years | RN New Architecture, Expo Modules |
| Native Islands | A long-standing hard problem; platform capability boundaries must be reported explicitly | Flutter Platform Views |
| Rendering | Prebuild shaders and pipelines | Flutter Impeller |
| Text input | Directly implement each platform's native protocol, with the largest engineering investment reserved | Flutter, Rune |
| Accessibility / semantics | An independent semantic tree mapped onto platform interfaces | Flutter Semantics |
| View API | Avoid DSLs and metaprogramming dependencies | SwiftUI result builder, Dart macros |
| Toolchain | Native projects generated by tools, native capabilities composed as packages + declarative configuration | Expo CNG / Config Plugins |
| Hot reload | Needs retained identity plus externally held state | Flutter, Rune |

## 8. Implications for the state-model argument

These points have been used in the design of the [Reactive core](../design/reactive-core.md):

1. The rebuild model also has the silent-stale-value problem (React's dependency arrays), so the asymmetry of "Signals fail
   silently, rebuild models are merely slower" is not that absolute.
2. The performance corrections for rebuild models all depend on a compiler (React Compiler, the Compose compiler, Swift macros).
   Rust cannot reach the same level unless proc-macro rewriting of view code is accepted. This weakens the feasibility of a pure
   rebuild approach in Rust.
3. Field-level tracking (SwiftUI `@Observable`) can serve as an enhancement of candidate B: implemented in Rust with
   `#[derive(Model)]`.
4. The large-scale move of the Web ecosystem to Signals shows that fine-grained reactivity is feasible in engineering; but on the
   Web the browser and the JS engine carry the runtime, so conclusions for Rust native UI cannot be derived directly.
