# 从 W3C 模块化规范审查无 kit 的 UI 能力

日期：2026-11-17。状态：规范调研与架构修订，未实施。
范围是当前 TR 发布版本，不声称已经穷尽最新编辑草稿；草稿不是正式 Recommendation，
文档状态也不代表浏览器或 Octara 的实现支持。

## 1. 结论与设计取舍

**core 必须通过公开 API 独立支持完整 UI；ui-kit 是普通使用者，不是获得完整输入和语义能力的必经入口。**
这是 Octara 的架构目标，非 W3C 对原生框架的要求。
原子性指职责集中、可组合，不是每个字段一个对象，也不是把所有原生输入细节转交应用。
基础编辑能力内部可以复杂；应用不应为不用 kit 而重写 IME。

## 2. 本次核对的规范

| 来源及本次发布状态 | 可借鉴的机制 | Octara 取舍 |
| --- | --- | --- |
| [CSS Display 3](https://www.w3.org/TR/2026/CRD-css-display-3-20260605/)，2026-06-05 Candidate Recommendation Draft | 元素结构与布局 box tree 不同；不产生自身盒子不等于删除语义 | 内容/组合与布局结果分别表达；不据此新增完整 DOM 或复制所有 display 类型 |
| [CSS Anchor Positioning 1](https://www.w3.org/TR/2026/WD-css-anchor-position-1-20260327/)，2026-03-27 Working Draft | 相对其他对象定位与尺寸、位置回退和溢出处理独立成模块 | 锚定是通用布局能力，不专属于 Popup；不要求字符串 anchor-name 或 CSS 解析器 |
| [Pointer Events 4](https://www.w3.org/TR/2026/WD-pointerevents4-20261008/)，2026-10-08 Working Draft | 统一不同指针设备，定义 capture/cancel 及直接操纵规则 | 普通应用和自定义控件都能使用必要的指针能力；不复制兼容 mouse 事件的整套 Web 映射 |
| [Input Events 2](https://www.w3.org/TR/2026/WD-input-events-2-20261015/)，2026-10-15 Working Draft | 编辑意图不等于物理按键；编辑前后事件及 IME 可取消性有明确区别 | 不从 keydown 猜全部文本编辑；不把业务拒绝回写等同于取消 OS 预编辑 |
| [EditContext](https://www.w3.org/TR/2026/WD-edit-context-20260910/)，2026-09-10 Working Draft | 文本、选择、composition 与几何组成 OS 输入上下文，可服务自绘编辑 | 编辑协议不能依赖某个 kit 输入框；普通输入提供便捷入口，自定义编辑可接入受约束协议 |
| [WAI-ARIA 1.3](https://www.w3.org/TR/2026/WD-wai-aria-1.3-20260604/)，2026-06-04 Working Draft | 角色、状态、关系形成可访问语义，框架管理的焦点与作者声明状态有区别 | 语义能力在 core 公开；Inspector 与 AX 共用事实，不增加独立可写 Agent 模型 |

[ARIA APG 的说明](https://www.w3.org/WAI/ARIA/apg/practices/read-me-first/)特别指出，role 不会自动提供键盘行为。
这是实践指南，不是另一份规范要求。Octara 应允许组合语义和行为，并提供可复用的基本激活/焦点能力，
避免每个无 kit 按钮都从原始按键重新实现；也不能让任意 role 设置暗中安装一整套控件。

## 3. 对之前“默认留在 kit”的修正

| 通用能力应当可由 core 公开使用 | kit 负责的组合与默认政策 |
| --- | --- |
| 容器、文本、图像、自绘、编辑内容及结构组合 | 具体控件的内容安排、尺寸和变体 |
| 布局、滚动、裁剪、展示层及锚定定位 | 菜单、提示、Dialog 的推荐位置和外观 |
| 指针事件/捕获、焦点操作、基本激活、必要的交互范围控制 | Tabs、Menu、Combobox 的导航与关闭政策 |
| 文本编辑、选择、composition、编辑几何及系统输入适配 | NumberField 的数字解析、格式化和提交规则 |
| 角色、名称、状态、描述和目标关系、语义动作 | Field 自动关联，标准控件的完整语义装配 |
| Signals、生命周期和任务 | 业务流程的便捷组合 |

这是能力清单，不要求每行一个新类型或 crate。公开面从已存在实现中提取最小稳定入口；
内部权限、节点分配器、缓存与挂载槽位仍不公开。
kit 可以有私有算法，但不能独占其他组件作者所需的窗口或编辑能力。
Root/Part 不是开放底层能力的前提，通用能力也不必提供全部排列组合的配置。

## 4. 简化标准与验证

采用一个直接的检验：在不依赖 octara-kit 的程序中，能否只用公开 API 完成：

1. 图标文字按钮：布局、基本激活、禁用、键盘和 AX/Agent 动作一致。
2. 自定义外观输入：中文 IME、选择、光标与候选窗几何正确，无需隐藏的替代输入框。
3. 锚定选择面板：滚动/缩放后位置正确，可声明非模态或所需交互范围；焦点和过期目标可解释。

这些是后续验收计划，本轮未编写或运行示例。
官方 kit 应通过同一公共入口实现对应能力，不使用普通库作者无法获得的绕行。
无需 kit 不等于无需框架：原生宿主、编辑协议、焦点管理、失效和生命周期仍由 core 负责。

此前四份契约中的详细重置仲裁、历史清除等保留为候选，不因引用 W3C 就升级为已确定要求。
W3C 输入事件与 EditContext 解决不同层次的问题，不应拼接成一套必须全量实现的协议。
优先验证“公开能力足够、机制不重复”，再决定具体名字与最小签名。
